## TL;DR

This repository is a complete, self-contained reference for creating
PortableApps.com Format (`.paf.exe`) packages: the directory layout, the
`appinfo.ini` and `installer.ini` files, the PortableApps.com Launcher (PAL)

alone and then create, code, compile, and test a correct PortableApps.com

## The 30-second model

A PortableApps.com package is a folder named `AppNamePortable`:

```
AppNamePortable\
  AppNamePortable.exe        <- generated launcher (compiled by PAL)
  help.html
  App\
    AppInfo\                 <- appinfo.ini, installer.ini, icons, Launcher\
    AppName\                 <- the actual application binaries
    DefaultData\             <- first-run defaults copied into Data\
  Data\                      <- ALL user data and settings live here
  Other\
    Help\Images\
    Source\                  <- launcher readme, licenses, custom code
```

Three configuration files drive everything:

- `App\AppInfo\appinfo.ini` — tells the PortableApps.com Platform what the
  app is (name, ID, version, category, license, dependencies).
- `App\AppInfo\Launcher\AppNamePortable.ini` — tells the generated launcher
  how to make the app portable (what to move, redirect, back up, restore).
- `App\AppInfo\installer.ini` — (optional) tells the PortableApps.com
  Installer how to build/install the package (downloads, extraction,
  optional components, upgrade behaviour).

Two official tools compile the deliverables:

- The **PortableApps.com Launcher Generator** reads the launcher INI and
  compiles `AppNamePortable.exe` with NSIS.
- The **PortableApps.com Installer** wizard reads `appinfo.ini` +
  `installer.ini` and compiles the distributable `AppNamePortable_X.Y.paf.exe`.

# AGENTS.md — Instructions for AI agents building PortableApps.com packages

You are using this repository as your knowledge base for creating
PortableApps.com Format packages (`.paf.exe` installers with a
PortableApps.com Launcher). Follow these rules exactly.

## Non-negotiable rules

1. **Never invent INI keys, section names, or values.** Every key you write
   in `appinfo.ini`, `installer.ini`, or a launcher INI must appear in
   `docs/01-format-spec.md`, `docs/02-installer-and-installer-ini.md`, or
   `docs/04-launcher-ini-reference.md`. Two documented exception classes
   live elsewhere: the production-verified environment variables in
   `docs/06-environment-variables.md`, and patterns in the mirrored
   production configs under `examples/real-world/` (borrow patterns
   only — reconcile every value against docs/01–04). If a behaviour you
   need is not covered by a documented key, the correct tool is custom
   NSIS code (`docs/05-launcher-advanced-custom-code.md`) — say so
   explicitly instead of guessing a key name.
2. **Case and spelling matter.** Section names and keys are matched by the
   tools as written in the references. Paths inside the package use Windows
   backslashes (`App\AppName\AppName.exe`).
3. **Versions:**
   - `[Format] Version` in `appinfo.ini` is the Format version: `3.9`.
   - `[Version] PackageVersion` is always exactly four numeric parts:
     `x.x.x.x` (for example `2.4.0.1`). No letters, no suffixes.
   - `[Version] DisplayVersion` is the human version (for example
     `2.4 Revision 1`). It never drives upgrade comparisons.
4. **Naming:**
   - Package folder: `AppNamePortable` (no spaces).
   - `AppID` equals the folder name for official-style packages.
   - Launcher INI file: `App\AppInfo\Launcher\<AppID>.ini` — the file name
     matches the AppID, for example `AppNamePortable.ini`. (Older packages
     used a single `launcher.ini`; the per-app named file inside the
     `Launcher` folder is the current convention.)
   - Generated launcher: `<AppID>.exe` in the package root, and
     `[Control] Start` in `appinfo.ini` must name exactly that file.
   - Installer output file: `<AppID>_<DisplayVersion>.paf.exe`, for example
     `AppNamePortable_1.2.paf.exe`. Online installers end in
     `_online.paf.exe`.
5. **Data separation is the whole point.** Binaries go in `App\`, all user
   data and settings go in `Data\`, sources/licences/readmes go in
   `Other\Source\`. Nothing user-specific may be written into `App\` at
   runtime, and no binaries may live in `Data\`.
6. **Leave no trace.** A package may touch the host registry/files while
   running only if it restores the host to its exact pre-run state on exit
   (back up a local copy's settings, restore them afterwards). See the
   Format's host-modification rule in `docs/01-format-spec.md`.
7. **Use the current tools.** Every release must be built with the current
   PortableApps.com Installer; a package built with an installer version
   more than 30 days superseded may not be released as current. Current
   versions are recorded in `docs/11-tools-and-versions.md`.
8. **Licensing is a hard gate, not a detail.** Check
   `docs/09-licensing-permissions-submission.md` before packaging anything
   you did not write. Freeware may only be packaged by its publisher or
   with the publisher's express consent, and only with the unmodified
   official installer.
9. **Start from the templates.** Copy `templates/MinimalAppPortable/` and
   the closest file in `examples/` — the mirrored production configs in
   `examples/real-world/` outrank the synthetic examples — then edit.
   Do not write configuration files from scratch from memory.
10. **Verify before declaring done.** Run every applicable item in
    `checklists/package-checklist.md` and
    `checklists/pre-release-checklist.md`. State plainly which checks were
    run and which could not be run (for example Windows-only runtime
    behaviour when working from a non-Windows machine) — label those
    **Unverified** rather than claiming success.

## Security rules (full treatment: `docs/18-security-privacy-and-abuse.md`)

- **Verify the base app before bundling it**: publisher's canonical URL,
  signature/published hash checked, source URL + SHA-256 recorded.
- **Online installers: HTTPS + `DownloadSHA256`, always.** A hash proves
  the payload is the file the packager chose, not that it is safe.
- **Custom code is code.** Read every line of any `.nsh` file before
  generating — never copy one unread from AppConfigs, a forum, or a
  template repo.
- **Least elevation**: `RunAsAdmin=none` by default; `try` before
  `force`; `compile-force` only with a written justification.
- **Never route around the services boundary**: services are disabled in
  PAL 2.2; do not implement them in custom code.
- **Scope the Force cleanup sections** to trees your trace inventory
  proved; they delete unconditionally on every exit and can destroy a
  local install's data.
- **No code through `Data`** — never move DLLs/scripts through it.
- **Never ship `Debug.nsh`** or a `Data\debug.log` in a release.

## Build order (always in this sequence)

1. Analyse the base app: where does it store settings (registry, `%APPDATA%`,
   `%LOCALAPPDATA%`, its own folder, documents folder)? Does it write
   anywhere else? Use a clean VM / Windows Sandbox + RegShot-style
   before/after comparison (`docs/07-end-to-end-workflow.md`).
2. Lay out the package tree from the template.
3. Write `appinfo.ini`.
4. Write the launcher INI to redirect/move/backup everything found in
   step 1.
5. Generate the launcher with the PortableApps.com Launcher Generator.
6. Test the extracted package (never only the installed one): first run,
   settings persistence, drive-letter change, second run, exit cleanliness,
   local-copy coexistence (`docs/08-testing-debugging-troubleshooting.md`).
7. Write `installer.ini` only if defaults are not enough (online download,
   optional components, upgrade preservation, etc.).
8. Build the `.paf.exe` with the PortableApps.com Installer wizard.
9. Install the built `.paf.exe` to a fresh location and repeat step 6
   against the installed copy.
10. Complete the pre-release checklist.

## Things that are always wrong

- `PackageVersion` with fewer/more than 4 parts, or containing text.
- A category that is not one of the 10 fixed values (Accessibility,
  Development, Education, Games, Graphics & Pictures, Internet,
  Music & Video, Office, Security, Utilities).
- A description longer than 512 characters in `appinfo.ini`.
- Double quotes inside `appinfo.ini` / `installer.ini` field values.
- Settings left in `%APPDATA%` or the registry after the app exits.
- Hard-coded drive letters or absolute paths in launcher configuration —
  use PAL variables (`%PAL:DataDir%`, `%PAL:AppDir%`, …) from
  `docs/06-environment-variables.md`.
- Including the generated `pac_installer_log.ini` in a source repository
  (add it to `.gitignore`).
- Copying the specification's full example `installer.ini` into a project —
  it is illustrative only. Build `installer.ini` from scratch with only
  the features the package needs.
- Modifying the PortableApps.com Installer's own code inside a package.
  Installer customisation goes in
  `Other\Source\PortableApps.comInstallerCustom.nsh` only.

# 01 — PortableApps.com Format 3.9 Specification

Based on the official PortableApps.com Format™ 3.9 specification
(2026-03-02), https://portableapps.com/development/portableapps.com_format

The Format governs the file/directory layout and operating behaviour of
portable apps. Packages are distributed as `.paf.exe` installer files built
by the PortableApps.com Installer.

## 1. Directory and file layout

```
AppNamePortable
+ App
   + AppInfo            configuration for the Platform + icons
      + FileTypeIcons   custom file-type icons (optional)
      + Launcher        launcher INI (+ custom.nsh) for PAL
   + AppName            the application binaries (usually)
   + DefaultData        first-run defaults copied into Data
+ Data                  ALL user data/settings; no binaries
+ Other
   + Help
      + Images          images used by help.html
   + Source             source, licenses, launcher readme, custom code
AppNamePortable.exe     the generated launcher (package root)
help.html               main help file (package root)
```

Rules:

- **Package root** contains only the launcher executable
  (`AppNamePortable.exe`) and `help.html` by default.
- **App** holds everything that makes up the application itself, usually in
  `App\AppName`. `AppInfo` holds configuration + icons and may hold the
  Launcher folder. `DefaultData` holds the default files that belong in
  `Data`; the launcher copies them into `Data` on first run when `Data`
  has no files yet.
- **Data** holds all user data — settings, configuration, profiles
  (Mozilla-style apps use `Data\profiles`, most apps use `Data\settings`).
  No application components (binaries) may be in `Data`. The launcher/app
  must be able to recreate `Data` and everything required in it if it is
  deleted.
- **Other** holds everything else: help images under `Other\Help\Images`,
  and source code, source licensing, installer source (if included), the
  launcher source/readme and license files under `Other\Source`.

## 2. appinfo.ini — complete reference

Location: `App\AppInfo\appinfo.ini`. INI format; do **not** put double
quotes inside field values.

### [Format]

| Key | Value |
|---|---|
| `Type` | Always `PortableApps.comFormat` (the only valid value) |
| `Version` | Format version the file follows; currently `3.9` |

### [Details]

| Key | Meaning |
|---|---|
| `Name` | Display name in the PortableApps.com Menu, e.g. `AppName Portable` |
| `AppID` | Globally unique ID. Official/publisher packages: the app name without spaces (`AppNamePortable`). Third-party packages must be suffixed: `AppNamePortable-example.com` (publisher domain) or `AppNamePortable-username` (PortableApps.com username, for individuals not working toward an official release). Allowed characters: letters, numbers, `.` `-` `+` `_` |
| `BaseAppName` | (Optional) Base app name when it differs from the launcher name. Only when legally required; otherwise omit |
| `Publisher` | Publisher name shown in hover tips and the app details screen. If repackaging someone else's app, list them too, e.g. `App Developer & PortableApps.com` |
| `Homepage` | Homepage of the **portable** app (not the base app) |
| `Donate` | (Optional) URL of a donations page |
| `Category` | Exactly one of: `Accessibility`, `Development`, `Education`, `Games`, `Graphics & Pictures`, `Internet`, `Music & Video`, `Office`, `Security`, `Utilities`. Use the English string even for non-English apps |
| `Description` | Brief description, **maximum 512 characters** |
| `Language` | `Multilingual`, or one of the fixed language strings: Afrikaans, Albanian, Arabic, Armenian, Basque, Belarusian, Bosnian, Breton, Bulgarian, Catalan, Cibemba, Croatian, Czech, Danish, Dutch, Efik, English, EnglishGB, Esperanto, Estonian, Farsi, Finnish, French, Galician, Georgian, German, Greek, Hebrew, Hindi, Hungarian, Icelandic, Igbo, Indonesian, Irish, Italian, Japanese, Khmer, Korean, Kurdish, Latvian, Lithuanian, Luxembourgish, Macedonian, Malagasy, Malay, Mongolian, Norwegian, NorwegianNynorsk, Pashto, Polish, Portuguese, PortugueseBR, Romanian, Russian, Serbian, SerbianLatin, SimpChinese, Slovak, Slovenian, Spanish, SpanishInternational, Swahili, Swedish, Thai, TradChinese, Turkish, Ukrainian, Uzbek, Valencian, Vietnamese, Welsh, Yoruba |
| `Trademarks` | (Optional) Trademark notices. Double quotes are converted to single quotes |
| `InstallType` | (Optional) Specific install type shown in the Platform (e.g. a language edition). With optional installer components, the installer updates this automatically from `installer.ini` |

### [License] — all values `true`/`false`

| Key | Meaning |
|---|---|
| `Shareable` | App may be copied drive-to-drive (without the `Data` directory) |
| `OpenSource` | Fully open source under an OSI-approved license |
| `Freeware` | Free of cost |
| `CommercialUse` | May be used in a business environment (does **not** grant commercial distribution) |
| `EULAVersion` | (Optional) Version of the EULA shown from `EULA.txt` at install time; defaults to `1` when a EULA is used |

### [Version]

| Key | Meaning |
|---|---|
| `PackageVersion` | Package version, **exactly `x.x.x.x`** numeric format, incremented with every public release. This is what the Platform compares for updates |
| `DisplayVersion` | Human-friendly version, e.g. `2.4 Revision 2` for PackageVersion `2.4.0.2` |

Versioning convention: `PackageVersion` is normally the base app's version
padded to four parts; the 4th part is the portable-package revision

### [SpecialPaths] (optional)

| Key | Meaning |
|---|---|
| `Plugins` | Path (inside the package) of a user-added plugins directory inside `App` (e.g. Firefox-style). Excluded from the free-space calculation on upgrade. Omit entirely if there is no plugins directory |

### [Dependencies] (optional)

| Key | Values / meaning |
|---|---|
| `UsesGhostscript` | `yes` / `no` / `optional` (optional = Ghostscript Portable adds features but is not required) |

| `UsesDotNetVersion` | Minimum .NET requirement. Bundled-runtime values: `5bundle`…`10bundle` (.NET 5–10 included with the app). Framework ranges: `4or3.5`, `4or3`, `4or2`. Specific Framework: `4.8`, `4.7.2`, `4.7.1`, `4.7`, `4.6.2`, `4.6.1`, `4.6`, `4.5.2`, `4.5.1`, `4.5`, `4`, `3.5`, `3`, `2`, `1.1`, `1`. | `RequiresAdmin` | `yes` if the app requires admin rights; default `no` |

### [Control]

| Key | Meaning |
|---|---|
| `Icons` | Number of icons (launch entries) the app has in the menu |
| `Start` | Command to start the app, relative to the package root — normally `AppNamePortable.exe` |

## 3. Icons

In `App\AppInfo`:

- Main icon: `appicon.ico` plus PNGs `appicon_16.png`, `appicon_32.png`,
  `appicon_75.png`, `appicon_128.png`, `appicon_256.png` (true colour with
  alpha; sizes match the suffixes).
- Extra icons for multi-icon apps: `appicon1.ico` / `appicon1_16.png` /
  `appicon1_32.png` / …, numbered to match `Start1`, `Start2`, …
- `appicon.ico` must contain: 16/32/48 px at 256 colours (8-bit),
  16/32/48 px at true colour + alpha (32-bit), and 256 px true colour +
  alpha as PNG.
- Custom file-type icons go in `App\AppInfo\FileTypeIcons` named after the
  extension: for `swf=custom`, provide `swf.ico`, `swf_16.png`,
  `swf_32.png`, `swf_128.png`. For `AllOtherIcons=custom`, the files are
  `AllOtherIcons.ico`, `AllOtherIcons_16.png`, etc.
- With `ExtractIcon` in use, `appicon.ico`/PNGs are unused and may be
  omitted; a generic `appicon.ico` is included for backwards compatibility.

## 4. Host PC modifications & portability (Format §5)

- A portable app **may** modify registry entries and local files while
  running, but must return them to their exact pre-run state on exit —
  including backing up and restoring a locally installed copy's settings.
- The app must keep working (settings, preferences, language, MRU file
  lists) as the drive letter changes between computers.
- This is the rule the Launcher exists to enforce; see
  `docs/03-launcher-overview.md`.

## 5. Format version history (recent)

- **3.9 (2026-03-02)** — custom legacy App ID in installer Legacy sections;
  multiple-EXE and Source copying in Legacy sections; more .NET directives;
  `ExitEXE`/`ExitParameters`; LegacyVersions handling.
- **3.8 (2024)** — `UseLightweight7Zip`; `RequiresAdmin`;
  `OptionalSectionPreSelectedIfLessThanWindows`; Inno Setup extraction;
  32/64-bit optional components; MD5 removed (SHA256 only).
- **3.7 (2023)** — `BaseAppIDARM64`; `DownloadSHA256`.
- **3.6 (2022)** — `Requires64bitOS`, `RequiresPortableApp`, 256 px PNG
  icon, full .NET Framework/Core value set, AppCompactor section removed
  (AppCompactor is no longer used for official releases).

# 02 — PortableApps.com Installer and installer.ini

The PortableApps.com Installer is the only permitted builder for
`.paf.exe` packages. Current version: **3.9.18 (2026-07-20)**. Every
release of an app in PortableApps.com Format must use the current
Installer; if a new Installer ships during a long test cycle, the older
one may be kept only if it is less than 30 days old on release day.

The installer is configured by `appinfo.ini` (see
`docs/01-format-spec.md`) plus the optional `installer.ini`, both in
`App\AppInfo`. **The whole `installer.ini` is optional.** Without it: the
`App` and `Other` directories are replaced on upgrade, `Data` is
preserved, the installer is single-language (per `appinfo.ini`) or
multilingual with all languages, and the installer source is not included.

> ⚠️ The full example `installer.ini` in the specification illustrates
> every option at once. **Never copy it into a project.** Create each
> project's `installer.ini` from scratch with only the features it needs.

## How building works

1. Lay out the complete package tree (`AppNamePortable\` with `App`,
   `Data`, `Other`, launcher exe, `help.html`).
2. Run `PortableApps.comInstaller.exe` (the Installer wizard) and point it
   at the package folder.
3. The wizard reads `appinfo.ini` + `installer.ini`, validates, and
   compiles `<AppID>_<DisplayVersion>.paf.exe` (online installers:
   `..._online.paf.exe`).
4. Test the produced `.paf.exe` by installing it to a **fresh** directory
   and running the installed copy — not the build tree.

The installer itself must not be modified. Customisation is only via
`installer.ini` and the custom-code file described below.

## installer.ini — complete reference

### [CheckRunning]

| Key | Meaning |
|---|---|
| `CloseEXE` | Custom EXE to check for/close when upgrading. Omit if it is the same as `[Control] Start` in `appinfo.ini`. `CloseEXE=NONE` (uppercase) disables the running check — use with caution |
| `CloseName` | Different display name for what will be closed. Omit if same as the app name in `appinfo.ini` |

### [Source]

| Key | Meaning |
|---|---|
| `IncludeInstallerSource` | `true` includes the PortableApps.com Installer source in the installed package |

### [MainDirectories]

Defaults: `App` removed, `Other` removed, `Data` preserved on upgrade.
Omit the section to keep defaults.

| Key | Meaning |
|---|---|
| `RemoveAppDirectory` | `true`/`false` — replace `App` on upgrade |
| `RemoveDataDirectory` | `true`/`false` — replace `Data` on upgrade (almost always `false`/omitted; removing user data on upgrade is destructive) |
| `RemoveOtherDirectory` | `true`/`false` — replace `Other` on upgrade |

### [OptionalComponents]

Enables a second, optional installer section (typically extra languages,
or 32-bit vs 64-bit components).

| Key | Meaning |
|---|---|
| `OptionalComponents` | `true` enables the optional section |
| `MainSectionTitle` | Default: `AppName Portable (English) [Required]`. Omit if happy with default |
| `MainSectionDescription` | Default: `Install the portable app` |
| `OptionalSectionTitle` | Default: `Additional Languages` |
| `OptionalSectionDescription` | Default: `Add multilingual support for this app` |
| `OptionalSectionSelectedInstallType` | `InstallType` written to `appinfo.ini` when the optional section is chosen. Default `Multilingual` |
| `OptionalSectionNotSelectedInstallType` | `InstallType` when not chosen. Default `English` |
| `OptionalSectionPreSelectedIfNonEnglishInstall` | Pre-select optional section if the installer runs in a non-English language. Default `true` |
| `OptionalSectionPreSelectedIfWindows32Bit` | Pre-select on 32-bit Windows. Default `false` |
| `OptionalSectionPreSelectedIfLessThanWindows` | Pre-select when Windows version is less than the integer given: XP=5, Vista=6, 7=7, 8=8, 8.1=9, 10=10, 11=11 |
| `OptionalSectionInstalledWhenSilent` | Install the optional section in silent (Platform-driven) installs. Default `true` when the optional components are not additional languages. Ignored when `OptionalSectionPreSelectedIfWindows32Bit=true` |
| `OptionalDirectory1`, `OptionalDirectory2`, … | Relative paths placed in the optional section, e.g. `OptionalDirectory1=App\AppName\locales` |
| `OptionalFile1`, `OptionalFile2`, … | Relative file patterns in the optional section, e.g. `OptionalFile1=App\AppName\*.lang` |

You **must** list the optional content with `OptionalDirectory#` and/or
`OptionalFile#` when an optional section exists.

### [CopyLocalFiles]

Copies files in from an existing local installation of the app at install
time (used by "portable-izer" style packages).

| Key | Meaning |
|---|---|
| `CopyLocalFiles` | `true` enables the section |
| `CopyFromRegPath` | Registry key holding the local install path, e.g. `HKLM\Software\AppName` |
| `CopyFromRegKey` | Value name within that key holding the path |
| `CopyFromRegRemoveDirectories` | Number of trailing path components to strip from the registry value to reach the folder to copy. If the value points at a file, count the file name as one. Example: value `C:\Program Files\AppName\bin\AppName.exe`, copy from `C:\Program Files\AppName` → `2` |
| `CopyFromDirectory` | Local directory to copy from, e.g. `%PROGRAMFILES%\AppName`. Also used as fallback when the registry lookup fails. Available variables: `%PROGRAMFILES%`, `%COMMONFILES%`, `%DESKTOP%`, `%WINDIR%`, `%SYSDIR%`, `%APPDATA%`, `%LOCALAPPDATA%`, `%TEMP%` |
| `CopyToDirectory` | Destination inside the package, usually `App\AppName`. Created if missing |

### [DownloadFiles] — online installers

Downloads file(s) at install time and optionally extracts them. This is
how legally non-redistributable apps are packaged: the `.paf.exe` is
small and fetches the real app from the publisher during install. The
resulting file name ends in `_online.paf.exe`.

| Key | Meaning |
|---|---|
| `AdditionalInstallSize` | Size (KB, number only) the downloaded content adds beyond what is inside the installer |
| `DownloadURL` | URL of the file to download |
| `DownloadKnockURL` | URL that must be fetched **before** `DownloadURL` (e.g. a page that sets a cookie/token) |
| `DownloadName` | Display name shown while downloading. Must be a valid DOS name — no `: " \` etc. |
| `DownloadFilename` | Local working file name; normally the same file name as in `DownloadURL` |
| `DownloadSHA256` | SHA-256 hash of the downloaded file; the installer verifies it. **Highly recommended** — an unverified download is a supply-chain hole. (MD5 support was removed in Format 3.8.) |
| `DownloadTo` | Copy the downloaded file into the package as-is at this relative path (e.g. `App\AppName`). Do not combine with extraction keys |
| `DownloadInnoExtractTo` | Extract a downloaded **Inno Setup** installer into this relative path (e.g. `App\AppName`) |
| `DownloadInnoExtractFrom` | With the above: sub-directory inside the Inno package to take, e.g. `{app}` |
| `DownloadCachedByPAc` | Marks that PortableApps.com caches this download for Platform App Store installs/updates (the standalone installer does not use the cache) |
| `AdvancedExtract1To` / `AdvancedExtract1Filter` | Extract from a ZIP or many installer EXEs with 7-Zip semantics. `…To` = relative destination (typically `App\AppName`); supports `<ROOT>` for the package root. `…Filter` = 7-Zip-style filter: `*` all files in root, `**` all files recursively, `*.txt`, `Src\*.cpp`, etc. Up to **10** numbered entries (`AdvancedExtract1…` … `AdvancedExtract10…`) |
| `DoubleExtractFilename` | For an archive inside the downloaded archive: the inner archive's file name (e.g. download `setup.exe` contains `data.zip`) |
| `DoubleExtract1To` / `DoubleExtract1Filter` | Same as AdvancedExtract, applied to the inner archive. Up to 10 entries. `…To` supports `<ROOT>` |
| `Download2URL` … `Download2DoubleExtract1Filter` | A complete second set of the above keys prefixed `Download2` (including `Download2AdvancedExtract…` and `Download2DoubleExtract…`) for a second downloadable file |
| `CustomCodeUses7zip` | `true` if installer custom code calls `7z.exe` itself. 7-Zip is auto-included when any Advanced/DoubleExtract key is used |
| `UseLightweight7Zip` | `true` to use the smaller `7za.exe` (7-Zip Extras) instead of `7z.exe`+`7z.dll`; saves a few hundred KB in minimal online installers. Default `false` |

Notes:

- Deprecated `Extract1To`-style keys are auto-converted to
  `AdvancedExtract` keys when an old package is compiled.
- Downloads generally do not work on Windows 2000; SHA-256 verification
  also requires post-2000 Windows.
- Always pin `DownloadSHA256`. If the publisher re-issues the file under
  the same URL with a different hash, the install will (correctly) fail —
  update the hash deliberately, never delete it to "fix" the failure.
- There is **no mirror/fallback download key**. `Download2*` describes a
  *second* downloadable file, not an alternative source for the first.
  If `DownloadURL` dies, the install fails; the fix is a new package
  release with a corrected URL and hash.
- What the Installer does with an interrupted download is not documented
  here (**Unverified**). Test it once for your package (start an online
  install, cut the network, observe) and record the result in your
  release notes.
- MSI and RAR inputs: the Installer lists MSI among the formats its
  online mode can extract, and `AdvancedExtract` uses 7-Zip semantics,
  but this knowledge base has no worked MSI example and does not
  enumerate every archive format 7-Zip accepts. Verify your exact input
  format with a test build before relying on it (**Unverified** beyond
  the Inno/ZIP cases in `examples/06-online-installer/`).

Put `EULA.txt` (Unicode, not ANSI) in `App\AppInfo`. The installer finds

`appinfo.ini`'s `[License]` when the EULA changes.

## Installer custom code (NSIS)

File: `Other\Source\PortableApps.comInstallerCustom.nsh` (Unicode, not
ANSI). It may define three macros:

| Macro | When it runs |
|---|---|
| `CustomCodePreInstall` | Before installation |
| `CustomCodePostInstall` | After installation |
| `CustomCodeOptionalCleanup` | At the start of installation when the optional section is **not** selected (for upgrades where the old install had it) |

Available beyond stock NSIS: `ConfigRead`, `ConfigReadS`, `ConfigWrite`,
`ConfigWriteS`, `GetParent`, `GetRoot`, `VersionCompare`, and LogicLib.
Set `CustomCodeUses7zip=true` in `[DownloadFiles]` if the code shells out
to 7-Zip.

## Installer logging

The installer writes `pac_installer_log.ini` into the installed
`App\AppInfo` directory, recording installer generation, installs,
wizard/installer versions and times. Do not alter or delete it (other
than via the official installer). **Exclude it from source control**
(`.gitignore`). Apps may read it to learn install time/method.

## Plugin installers

The Installer can also build **plugin installers** that add files to an
existing portable app:

- Configuration is a single `plugininstaller.ini` in `App\AppInfo`,
  combining everything that would be in `appinfo.ini` + `installer.ini`.
- `[Details]` gains `PluginName=` (e.g. `Adobe Flash for Firefox Portable`).
- All `[MainDirectories]` removal options default to `false`.
- EULA file is `PluginEULA.txt` instead of `EULA.txt`.
- Custom code file is `PortableApps.comInstallerPluginCustom.nsh` in
  `Other\Source`.
- Build a normal-looking package tree containing **only** the plugin's
  files; `App\AppInfo` contains only `plugininstaller.ini`.
- **CommonFiles installers** (install into `X:\PortableApps\CommonFiles`,
  for shared components like Java, designated by PortableApps.com): add
  `PluginType=CommonFiles` to `[Details]`. For these, `App` removal
  defaults to `true` (the whole `CommonFiles\<AppID>` folder is replaced).

## Installer behaviour worth knowing

- Installing into `C:\Program Files` (or equivalent) is **not supported**
  — portable apps install to a user-chosen folder, normally under a
  `PortableApps` directory on a portable drive or local disk.
- On upgrade, the installer checks whether the app is running
  (`[CheckRunning]`) and offers to close it before replacing files.
- In silent mode (driven by the Platform's app store/updater), prompts
  are suppressed and `[OptionalComponents]` silent rules apply.
- The installer appends the app folder name to a `/DESTINATION=`-style
  target: the user picks the **parent** (e.g. `X:\PortableApps`), the
  package installs to `X:\PortableApps\AppNamePortable`.

# 03 — PortableApps.com Launcher (PAL) Overview

The PortableApps.com Launcher makes an ordinary Windows application
portable **without modifying the application's code**. Current version:
**2.2.9 (2024-05-25)**; the manual documents PAL 2.2.

## What it is

PAL is a **generator**, not a runtime library:

1. You write one configuration file:
   `App\AppInfo\Launcher\<AppID>.ini` (see
   `docs/04-launcher-ini-reference.md`).
2. You run the **PortableApps.com Launcher Generator**
   (`PortableApps.comLauncherGenerator.exe` from the Launcher package)
   and point it at your package folder.
3. The Generator validates the INI and **compiles** a small native
   launcher, `<AppID>.exe`, into the package root, using NSIS. Only the
   subsystems you activated (`[Activate]`) are compiled in, which keeps
   the launcher small and fast.
4. End users run `<AppID>.exe`. There is no separate PAL runtime to
   install.

Changing the INI — especially `[Activate]` values that add plug-ins —
requires **regenerating** the launcher. The generated exe and the INI must
always be kept in sync; ship the INI in the package (in
`App\AppInfo\Launcher`) so the package can be rebuilt.

**Generator prerequisites (manual, quickstart):** install the Launcher
and **NSIS Portable, the Unicode variant** — for automatic detection,
NSIS Portable must sit in a **sibling directory named `NSISPortable`**
next to the Launcher (recommended layout: `X:\PortableApps\PortableApps.comLauncher`
and `X:\PortableApps\NSISPortable`). The ANSI NSIS variant is not used.
Run the Generator from its install directory or from the Platform, pass
it the package's main folder (`AppNamePortable`), and it compiles
`<AppID>.exe` into that folder. Re-run it after **any** change to the
launcher INI, `Custom.nsh`, or `Debug.nsh` — all three are compiled in.
(The current Launcher release notes also describe an NSIS core bundled
with the builder; the manual's sibling-install instruction above is the
documented 2.2 route — if your Generator finds NSIS by itself, that is
the bundled core at work.)

## What the generated launcher does at runtime

In order, roughly:

1. **Pre-flight checks** — OS version (`MinOS`/`MaxOS`), single-instance
   rules, UNC/spaces-in-path policies, admin elevation (`RunAsAdmin`),
   Java discovery (`[Activate] Java`).
2. **First-run setup** — if `Data` is empty/missing, populate it from
   `App\DefaultData`.
3. **Live mode decision** — if the package is on read-only media (or the
   user set `RunLocally=true`), copy app/data to a temp folder and run
   from there (`[LiveMode]`).
4. **Backup of local state** — for every registry key, file, and directory
   PAL manages, any pre-existing **local** copy's data is backed up (e.g.
   `<name>-BackupBy<AppID>`), so a locally installed copy of the same app
   is never harmed.
5. **Redirection in** — portable registry keys are imported from
   `Data\settings\*.reg`; portable files/directories are copied/moved to
   the locations the app expects (`%APPDATA%`, etc.); `[FileWriteN]`
   rewrites stored paths for the current drive/location; `[Environment]`
   variables are set; `[RegistryValueWrite]` values are applied;
   a contained TEMP directory is assigned (`CleanTemp`).
6. **Splash screen** (unless disabled) and **launch** of
   `ProgramExecutable` with `CommandLineArguments` plus any arguments the
   user passed to the launcher.
7. **Waiting** — the launcher waits for the app (and any `WaitForEXE`
   children) to exit, so cleanup cannot run early.
8. **Redirection back out** — changed registry keys are exported back to
   `Data\settings\*.reg`; files/directories are moved back into `Data`;
   values written only for the run are removed; cleanup sections delete
   leftovers (`[RegistryCleanup*]`, `[DirectoriesCleanup*]`,
   `[QtKeysCleanup]`).
9. **Restore of local state** — the backups from step 4 are restored, so
   the host PC is exactly as it was before the run. This is how PAL
   satisfies the Format's host-modification rule.

If the launcher detects an unclean previous exit (crash, power loss), it
recovers on the next launch: it restores the local backups and re-saves
the portable state rather than losing either.

## The portability techniques (choose per trace)

From least to most invasive — prefer the earliest that works:

1. **The app's own portable mode** — a command-line switch, a
   settings-next-to-exe mode, or an official portable build. Use
   `CommandLineArguments` / `[Environment]` to engage it.
2. **Environment redirection** — many apps honour variables like
   `%APPDATA%`-style overrides or their own `*_HOME` variable; set them in
   `[Environment]` to point inside `Data`.
3. **File/directory moves** — `[FilesMove]` / `[DirectoriesMove]` shuttle
   settings between `Data` and the expected location around the run.
4. **Registry save/restore** — `[RegistryKeys]` (+ cleanup sections).
5. **Path rewriting** — `[FileWriteN]` fixes absolute paths stored inside
   settings files when the drive letter or folder changes.
6. **Value writes** — `[RegistryValueWrite]` forces individual values for
   the portable run.
7. **Custom NSIS code** — for anything the INI cannot express; see
   `docs/05-launcher-advanced-custom-code.md`.

## User configuration

End users can place `<AppID>.ini` next to the launcher exe to set
`AdditionalParameters`, `DisableSplashScreen`, and `RunLocally` — see the
end of `docs/04-launcher-ini-reference.md`. Packages ship an example of
this file in `Other\Source`.

## Hard limits to know

- PAL cannot make an app portable if it requires a kernel driver or a
  permanently installed Windows service — `[ServiceN]` exists in the INI
  reference but **services are currently disabled** in PAL 2.2.
- PAL launchers are Windows executables compiled with NSIS; there is no
  macOS/Linux variant.
- The launcher can only clean up what it knows about: every trace the app
  leaves must be covered by the INI (or custom code), which is why the
  analysis phase in `docs/07-end-to-end-workflow.md` matters.

# 04 — Launcher INI Complete Reference (PAL 2.2)

Source: official PortableApps.com Launcher 2.2 manual,
https://portableapps.com/manuals/PortableApps.comLauncher/ (`ref/launcher.ini/*`).
Verified against the manual on 2026-11-16.

## File identity

- The file is **never** literally named `launcher.ini` in a package. It is
  `App\AppInfo\Launcher\<AppID>.ini` — the base name matches the launcher
  executable (`AppNamePortable.exe` → `AppNamePortable.ini`). "launcher.ini"
  is the manual's shorthand.
- INI syntax: `[Section]` headers (CamelCase by convention), `Key=value`,
  comment lines start with `;`. **Inline comments are NOT permitted.**
- Quoting: if a value's first and last characters are the same quote (`'`
  or `"`), the quotes are stripped — a pure character check, no escaping.
  This matters for `CommandLineArguments` containing paths with spaces.
- **There is no safety net for INI keys.** A misspelled or invented key
  is not an error — PAL simply never acts on it, and the feature it was
  meant to enable silently does not happen. (Custom code is the opposite:
  an unknown `${Segment…}` macro fails the Generator compile —
  `docs/05-launcher-advanced-custom-code.md`.) Diff every key against
  this file before generating.

## Definitive section list (PAL 2.2)

`[Launch]`, `[Activate]`, `[LiveMode]`, `[Environment]`, `[RegistryKeys]`,
`[RegistryValueWrite]`, `[RegistryCleanupIfEmpty]`,
`[RegistryCleanupForce]`, `[RegistryValueBackupDelete]`,
`[QtKeysCleanup]`, `[FileWriteN]`, `[FilesMove]`, `[DirectoriesMove]`,
`[DirectoriesCleanupIfEmpty]`, `[DirectoriesCleanupForce]`, `[Language]`,
`[LanguageStrings]`, `[LanguageFile]`, `[ServiceN]`

**Do not use** (commonly guessed, but **not** in PAL 2.2): a `[Qt]`
section (it is `[QtKeysCleanup]`), a `[Services]` section (it is
`[ServiceN]`), `[FileExtensions]`/`[URIProtocols]`/`[ProtocolExtensions]`
sections, `[Launch] AdditionalParametersAllowed`, `[Launch] DosName`,
`[Activate] VB6RunTime`, a `[Dependencies]` section, or a `[Control]`
section (that belongs to `appinfo.ini`). File associations are handled via
registry sections or custom code.

## [Launch]

| Key | Values / default | Meaning |
|---|---|---|
| `ProgramExecutable` | Path, **mandatory** | Program to launch, **relative to the package's `App` directory**. `App\AppName\AppName.exe` → `ProgramExecutable=AppName\AppName.exe`. With `[Activate] Java=require`, `java.exe`/`javaw.exe` is rewritten to the found JRE binary |
| `ProgramExecutable64` | Path, optional (2.1+) | Override on 64-bit Windows. Only ship 64-bit builds when there is significant benefit or a requirement |
| `ProgramExecutableWhenParameters` | Path, optional | Override used **only when arguments are passed** to the launcher (e.g. menu exe normally, compiler exe when a file is passed) |
| `ProgramExecutableWhenParameters64` | Path, optional (2.1+) | 64-bit override of the above. Lookup order: WhenParameters64 → 64 → WhenParameters → base |
| `CommandLineArguments` | String, optional | Arguments **always** passed to the app (e.g. to point it at portable data). Quote paths with spaces: `CommandLineArguments='-d "%PAL:DataDir%\settings"'`. Envsub applies. Arguments the *user* passes to the launcher exe are forwarded separately |
| `WorkingDirectory` | Path, optional | Launch working directory. **Avoid when possible** — it breaks passing multiple relative files; a single file is auto-corrected. Prefer adding the app dir to `PATH` via `[Environment]` |
| `MinOS` | `none`/`2000`/`XP`/`2003`/`Vista`/`2008`/`7`/`2008 R2`; default `none` (2.1+) | Minimum Windows version; lower versions get a message and the app does not run |
| `MaxOS` | Same values; default `none` (2.1+) | Maximum Windows version. Use cautiously |
| `RunAsAdmin` | `force`/`try`/`compile-force`/`none`; default `none` (`compile-force` 2.1+) | `force`: UAC prompt; failure/cancel = exit with a message. `try`: prompt; if not elevated, warn and continue. `compile-force`: bakes `RequestExecutionLevel admin` into the exe (requires regenerating the launcher; OS handles elevation, no friendly message) |
| `RunAsAdmin2000` / `RunAsAdminXP` / `RunAsAdmin2003` / `RunAsAdminVista` / `RunAsAdmin2008` / `RunAsAdmin7` / `RunAsAdmin2008R2` | `force`/`try`/`none` (2.1+) | Per-OS overrides of `RunAsAdmin`. Pattern: `RunAsAdmin=force` + `RunAsAdminXP=none` for apps needing admin only on Vista+ |
| `CleanTemp` | `true`/`false`; default `true` | When true, the app gets a contained temp dir `%TEMP%\AppNamePortableTemp`, deleted on exit. With `WaitForProgram=false`, temp goes to `Data\temp` and is deleted on next start instead. Set `false` only if the app provably leaves nothing in TEMP |
| `SinglePortableAppInstance` | `true`/`false`; default `false` | `true`: only one instance of the **portable** copy; a second portable launch aborts silently |
| `SingleAppInstance` | `true`/`false`; default `true` | If a **local** copy is already running, abort with an error. Does not affect a second portable instance. Set `false` only if local+portable may run together safely (never when settings live in `%APPDATA%`/registry). For Launch4J Java apps, set `false` and use `CloseEXE` |
| `CloseEXE` | File name only, optional | A **different** exe that must be closed before starting (mainly Java/Launch4J apps whose real process differs from `ProgramExecutable`) |
| `SplashTime` | Milliseconds; default `1500` | Splash screen duration. Do not inflate it. Users can disable the splash entirely (user config) |
| `LaunchAppAfterSplash` | `true`/`false`; default `false` | Wait for the splash to finish before launching (for full-screen/resolution-changing apps) |
| `WaitForProgram` | `true`/`false`; default `true` | `false`: launcher does not wait for exit. **Only** safe when no registry handling and no file moves are used (all settings redirected by args/env vars). Ignored in Live mode |
| `WaitForOtherInstances` | `true`/`false`; default `true` | May be `false` for single-instance apps that forward to the first instance **and cannot restart themselves**. Never `false` for self-restarting apps (e.g. Firefox) — cleanup would run while the app still runs |
| `WaitForEXE1`, `WaitForEXE2`, … | File name | Extra executables to wait for when `ProgramExecutable` is a stub that spawns the real app. Number sequentially from 1 |
| `RefreshShellIcons` | `before`/`after`/`both`/`none`; default `none` | Refresh Explorer icons around launch, for apps whose file-type registrations PAL handles/cleans. With `[RegistryKeys]` handling, use `both` |
| `HideCommandLineWindow` | `true`/`false`; default `false` | Hide a console window produced by the app |
| `DirectoryMoveOK` | `yes`/`warn`/`no`; default `warn` (2.1+) | Whether the **package folder itself** may be moved (drive-letter changes must always work regardless). Set `yes` only after designing for moves, typically with `[FileWriteN]` + `%PAL:LastPackagePartialDir%`/`%PAL:PackagePartialDir%` |
| `NoSpacesInPath` | `true`/`false`; default `false` | `true`: show a clear error if the package path contains spaces instead of letting the app fail obscurely |
| `SupportsUNC` | `yes`/`warn`/`no`; default `warn` (2.2+) | Running from a UNC path `\\server\share\…`. Only `yes` after actually testing UNC — some apps corrupt data on UNC |
| `AppName` | String, **deprecated** | Non-portable app name for the "already running" error. Derived from `appinfo.ini` when unset; leave unset |

## [Activate]

Tells PAL which subsystems to compile in. Changing a value that adds a
plug-in **requires regenerating the launcher**.

| Key | Values / default | Meaning |
|---|---|---|
| `Registry` | `true`/`false`; default `false` | **Must be `true` for ANY registry section to be parsed at all** (`[RegistryKeys]`, `[RegistryValueWrite]`, `[RegistryCleanup*]`, `[RegistryValueBackupDelete]`, `[QtKeysCleanup]`) |
| `Java` | `none`/`find`/`require`; default `none` | `find`: locate a JRE if present and set `%JAVA_HOME%` (path may not exist). `require`: abort if no Java found; `ProgramExecutable=javaw.exe`/`java.exe` is rewritten to the JRE binary. With `require`, consider `WaitForProgram=false`/`WaitForOtherInstances=false` or cleanup may match other apps' `javaw.exe` |
| `XML` | `true`/`false`; default `false` | Required for `[FileWriteN]`/`[LanguageFile]` types `XML attribute`/`XML text`. Adds the NSIS XML plug-in (~60 KB). PAL warns at generation time if XML features are used without it |

No other `[Activate]` keys exist in 2.2.

## [LiveMode]

Behaviour when the package is on read-only media ("running locally"):
needed parts are copied to a writable temp location, run, then deleted.

| Key | Values / default | Meaning |
|---|---|---|
| `CopyApp` | `true`/`false`; default `true` | Whether the app itself must be copied to run in Live mode. Affects `%PAL:AppDir%` in Live mode |
| `CopyData` | **Obsolete** | Removed; data is always copied in Live mode. Do not use |

## [Environment]

Arbitrary `NAME=value` pairs — no fixed keys. Each sets an environment
variable **for the launched app and its children only**. Parsed in file
order, **before** all other active sections, so variables defined here can
be reused later in the file. Envsub applies to values.

```ini
[Environment]
PATH=%PATH%;%PAL:AppDir%\AppName
APPNAME_HOME=%PAL:DataDir%\settings
```

Long paths can be defined once as pseudo-variables (including transformed
forms such as `%PAL:DataDir:DoubleBackslash%`) and referenced elsewhere.

## Registry sections — all require `[Activate] Registry=true`

Roots are written short: `HKCU`, `HKLM`, `HKCR`, `HKU`, …

### [RegistryKeys]

Format: `filename=HKCU\Software\AppName`

- The key subtree is imported from / saved to `Data\settings\<filename>.reg`.
- A pre-existing local key is backed up before the run and restored after.
- Special filename `-`: `-=HKCU\Software\AppName` protects the local key
  and **discards** the portable app's changes (nothing saved).
- To fix drive letters inside a saved `.reg`, add a `[FileWriteN]`
  `Type=Replace` targeting that `.reg` file.

### [RegistryValueWrite]

Format: the **key name is the full path including the value name**;
the value is `REG_TYPE:value` (prefix optional, defaults to `REG_SZ` —
write it explicitly if the value itself could contain a colon).

```ini
[RegistryValueWrite]
HKCU\Software\AppName\Settings\SavePath=REG_SZ:%PAL:DataDir%
HKCU\Software\AppName\Settings\Count=REG_DWORD:16
```

Use it to set values only for the portable run (e.g. pointing the app at
portable paths, disabling association writes).

### [RegistryValueBackupDelete]

Format: consecutive integers from 1: `1=HKCU\Software\Publisher\AppName\SomeValue`

Each listed **value** is backed up before and restored after the run, but
any value the portable app sets is **deleted** (for values not worth saving).

### [RegistryCleanupIfEmpty]

Format: consecutive integers from 1: `1=HKCU\Software\Publisher`

Listed keys are deleted after the run **only if empty** — for parent trees
left behind empty.

### [RegistryCleanupForce]

Format: consecutive integers from 1. Listed keys are **unconditionally
removed with contents** after the run — for trees of useless/temp data.

> **Warning — this can destroy a local install's data.** If a listed key
> is one the locally installed copy of the app also uses, force cleanup
> deletes the *local* settings on every exit. The safe alternatives:
> `[RegistryKeys]` (the local key is backed up and restored) or the `-`
> filename form in `[RegistryKeys]` (protects the local key and discards
> the portable app's changes). Reserve force cleanup for keys only the
> portable app creates. See `docs/17-failure-mode-reference.md` §E.

### [QtKeysCleanup]

Cleans Qt's per-path cache keys under
`HKCU\Software\Trolltech\OrganizationDefaults\`. Entries (integers from 1)
are the offending key with that prefix **and** the trailing portable path
stripped:

```ini
[QtKeysCleanup]
1=Qt Factory Cache 4.6\com.trolltech.Qt.QImageIOHandlerFactoryInterface:
2=Qt Plugin Cache 4.6.false
```

## [FileWriteN] — `[FileWrite1]`, `[FileWrite2]`, …

Writes into files **before launch** (typically updating stored paths when
the package moved). The target file **must already exist** or the section
is silently skipped.

| Key | Required for | Meaning |
|---|---|---|
| `Type` | Always (mandatory) | `ConfigWrite` / `INI` / `Replace` / `XML attribute` / `XML text` (XML types need `[Activate] XML=true`) |
| `File` | Always | File to modify. Envsub applies |
| `Entry` | `ConfigWrite` | Line prefix to find; `Value` is written onto that line, or appended at end of file if not found. Include all leading whitespace; quote the string if it has leading/trailing whitespace |
| `Section` + `Key` + `Value` | `INI` | Write `Value` into an INI file's `Section`/`Key` |
| `Value` | `ConfigWrite`, `INI`, XML types | Value to write. For `ConfigWrite` into XML-like files, include closing markup yourself (e.g. `%PAL:DataDir%\settings</config>`) or use the XML types |
| `Find` + `Replace` | `Replace` | Find-and-replace in the file (the drive-letter/path update mechanism). If after envsub `Replace` == `Find`, the replacement is skipped |
| `Attribute` + `XPath` | XML types | Attribute to set / XPath locating the node |
| `CaseSensitive` | Optional, `ConfigWrite`/`Replace` | Default `false`. Case-sensitive search is faster |
| `Encoding` | Optional, `Replace` only | `auto` (default, detect from BOM) / `ANSI` / `UTF-16LE`. Set `UTF-16LE` for a UTF-16LE file missing its BOM. `ConfigWrite`/`INI` auto-detect encoding themselves |

### The path-migration triple (required pattern)

Any stored file that can contain an absolute path needs **three** `Replace`
sections per file, in this order — most specific first. A stored path can
take any of the three forms, and missing one leaves stale paths behind
(the classic symptom: the app works on the first machine and breaks, or
points at the old drive, after the package moves). This is the pattern the
official Application Template teaches and production packages use
(Notepad++ Portable repeats it for five files, `[FileWrite1]`–`[FileWrite15]`):

```ini
[FileWrite1]
Type=Replace
File=%PAL:DataDir%\Config\config.xml
Find=%PAL:LastDrive%%PAL:LastPackagePartialDir%\
Replace=%PAL:Drive%%PAL:PackagePartialDir%\

[FileWrite2]
Type=Replace
File=%PAL:DataDir%\Config\config.xml
Find=%PAL:LastPortableAppsBaseDir%\
Replace=%PAL:PortableAppsBaseDir%\

[FileWrite3]
Type=Replace
File=%PAL:DataDir%\Config\config.xml
Find=%PAL:LastDrive%\
Replace=%PAL:Drive%\
```

Variants used by production packages:

- **Inside a saved `.reg` file**, paths are stored with doubled
  backslashes, so use the `:DoubleBackslash` forms and a doubled trailing
  backslash (`Find=%PAL:LastDrive%%PAL:LastPackagePartialDir:DoubleBackslash%\\`).
- **`REG_BINARY` values** in a `.reg` store the drive as hex bytes; add a
  fourth replace: `Find=%PAL:LastDriveHex%,00,3a,00` →
  `Replace=%PAL:DriveHex%,00,3a,00`.
- Set `DirectoryMoveOK=yes` in `[Launch]` only once every path-storing
  file has its triple.

### Working on the saved `.reg` file itself

`[FileWriteN]` may target the `.reg` files that `[RegistryKeys]` saves
into `Data\settings\` — they are plain files before import. Two production
uses (7-Zip Portable, mirrored in
[`../examples/real-world/7zip/`](../examples/real-world/7zip/)):

- `Type=INI` with `Section=HKEY_CURRENT_USER\Software\…` to rewrite a
  single value inside the `.reg` (there: injecting `%PAL:LanguageCustom%`
  as the app's `Lang` value).
- The migration triple in `:DoubleBackslash` form (above) to fix paths
  the app stored in its registry keys.

## Filesystem sections (wildcards supported since 2.1; envsub applies)

### [FilesMove]

Format: `filename=target directory`

```ini
[FilesMove]
settings\file.txt=%PAL:AppDir%\AppName
```

- `filename` is **relative to `Data\`**. The target is the **directory**
  the file is copied into while running — do **not** include the file name.
- An existing local target file is backed up (to
  `<filename>-BackupBy<AppID>`) and restored at exit; the portable file
  moves back to `Data\` at exit.
- The folder containing the file **inside `Data\` must already exist** or
  the file will not be saved — keep files at `Data\` root or in
  `Data\settings`, or create the folder via `DefaultData`.

### [DirectoriesMove]

Format: `directory=target location`

```ini
[DirectoriesMove]
AppNameConfig=%APPDATA%\Publisher\AppName
```

- `directory` is relative to `Data\`; the target **includes the directory
  name itself** (`Data\<directory>\*.*` → `<target>\*.*`).
- A pre-existing target is backed up (to `<target>-BackupBy<AppID>`) and
  restored at exit.
- Special source `-`: `-=<target>` protects the local directory and
  **discards** changes.
- The **parent** folder inside `Data\` must exist — use a top-level
  directory name. **Never use `settings` as the key**: `Data\settings`
  holds the registry `.reg` files; moving it loses data.

### [DirectoriesCleanupIfEmpty]

Format: integers from 1 (`1=%APPDATA%\Publisher`). Listed directories are
removed after the run **only if empty**.

### [DirectoriesCleanupForce]

Format: integers from 1. Listed directories are **unconditionally
removed** after the run. To protect local data instead of destroying it,
use `[DirectoriesMove]` with key `-`.

## Language sections

These build the custom variable `%PAL:LanguageCustom%` (usable anywhere
envsub applies) from the Platform language plus app-specific mappings.

### [Language]

| Key | Meaning |
|---|---|
| `Base` | **Mandatory if the section is used.** Base string to derive from — normally exactly one language variable, e.g. `Base=%PortableApps.comLanguageCode%` |
| `Default` | Optional. Value used when the base value is not a key in `[LanguageStrings]`; if unset, the base value itself is used |
| `CheckIfExists` | Optional. File to test (append `\*.*` to test a directory); may use `%PAL:LanguageCustom%`. If it does not exist, fall back to `DefaultIfNotExists` |
| `DefaultIfNotExists` | Optional. Fallback value when the `CheckIfExists` test fails |

### [LanguageStrings]

Arbitrary pairs: the `[Language] Base` value is looked up **as a key name**
here, and the matching value (after envsub) becomes `%PAL:LanguageCustom%`.

```ini
[LanguageStrings]
en=English
pt-br=PortugueseBR
```

### [LanguageFile]

Reads `%PAL:LanguageCustom%` **from a file** — for launches outside the
Platform, where no Platform language variables exist. Keys mirror
`[FileWriteN]` reading: `Type` (`ConfigRead`/`INI`/`XML attribute`/`XML text`,
mandatory), `File` (mandatory), `Entry` (for `ConfigRead`), `Section`/`Key`
(for `INI`), `Attribute`/`XPath` (XML types; need `[Activate] XML=true`),
`CaseSensitive` (for `ConfigRead`), and `TrimRight` (strip this suffix from
the read string, e.g. a file extension or closing tag). `ConfigRead`/`INI`
auto-detect encoding from the BOM.

## [ServiceN] — `[Service1]`, `[Service2]`, …

> ⚠️ **Services are currently disabled in the PortableApps.com Launcher.**
> This section is documented but non-functional in PAL 2.2.

Keys: `Name` (mandatory), `Path` (mandatory), `Type`
(`service`/`driver-kernel`/`driver-file-system`, default `service`),
`User` (`none`/`LocalService`/`NetworkService`, default `none` =
LocalSystem), `Display`, `Dependencies` (comma-separated), `Description`,
`IfExists` (`skip`/`replace`, default `skip`; currently no effect except a
warning for `replace`).

## User configuration file (`<AppID>.ini` next to the exe)

A **different file** from the launcher INI: it sits in the package root
next to `<AppID>.exe` with the same base name, and lets the *end user*
override behaviour. Packages ship an example as
`Other\Source\<AppID>.ini`; the user copies it to the root and renames it.
No section header is required.

| Key | Values / default | Meaning |
|---|---|---|
| `AdditionalParameters` | String; default empty | Extra command-line parameters passed to the app, in addition to `[Launch] CommandLineArguments` and parameters given to the launcher exe |
| `DisableSplashScreen` | `true`/`false`; default `false` | Suppresses the splash screen |
| `RunLocally` | `true`/`false`; default `false` | Forces Live mode: copy needed app/data to a temp folder on the host, run, delete afterwards |

Custom code can define **additional** app-specific user keys via
`${ReadUserConfig}` — those are documented in that app's `help.html`, are
not standard PAL keys, and booleans use `true`/`false` by convention.
There is no standard user key named `LiveMode`; the key is `RunLocally`.

## Minimal valid example (verified keys only)

```ini
[Launch]
ProgramExecutable=AppName\AppName.exe
DirectoryMoveOK=yes
SupportsUNC=yes

[Activate]
Registry=true

[RegistryKeys]
AppName=HKCU\Software\AppName

[DirectoriesMove]
AppNameConfig=%APPDATA%\AppName
```

# 05 — Launcher Advanced Topics: Segments and Custom Code

Most packages need **no** custom code. Write it only when the launcher
INI (docs/04) cannot express a behaviour — and check the Development
forum first, because there is usually an INI way.

Sources: PAL 2.2 manual, `advanced/custom.html`; PAL 2.1 release notes;
official PortableApps.com forum guidance from the PAL developers.

## The Custom.nsh file

| PAL version | Location |
|---|---|
| **2.1 and later (current)** | `App\AppInfo\Launcher\Custom.nsh` |
| 2.0 (legacy) | `Other\Source\PortableApps.comLauncherCustom.nsh` |

The Generator automatically upgrades the legacy path/name when it first
compiles a package that still uses it. The manual's custom-code page
still shows the old `Other\Source` location in one sentence — that is a
known documentation error (acknowledged by the developers in the forum);
the release notes and the Generator's actual behaviour put the file in
`App\AppInfo\Launcher\Custom.nsh`. After editing `Custom.nsh`, the
launcher must be **regenerated** — custom code is compiled in, not read
at runtime.

All non-debugging launcher modifications go in this one file. Do not edit
PAL's own segment files or the generated launcher.

## Segments and hooks

PAL is built from **segments** (one per feature: FilesMove, RegistryKeys,
Environment, …). Each segment runs code at defined points of the
launcher lifecycle through **hooks**. A custom segment adds your own
hooks to that lifecycle.

File structure:

```nsh
${SegmentFile}

; Optional: segment-specific macros/functions first, prefixed with
; _YourSegmentName_ by convention, then any Var declarations.

${SegmentInit}
    ; ... NSIS code ...
!macroend

${SegmentPrePrimary}
    ; ... NSIS code ...
!macroend
```

Rules:

- The **first line** of `Custom.nsh` is `${SegmentFile}`.
- Each hook is written as `${Segment<Hook>}` … `!macroend`.
- Custom macros/functions should be prefixed with the segment name
  (e.g. a "Start" macro in a FilesMove-like segment becomes
  `_FilesMove_Start`) and placed immediately after `${SegmentFile}`,
  before variable declarations.
- LogicLib is already included — `${If}` / `${ElseIf}` / `${EndIf}` and
  friends are available with no extra include.

### Hook names (lifecycle order)

Verified hook macros include:

| Hook | When it runs |
|---|---|
| `${Segment.onInit}` | In NSIS `.onInit` — earliest possible point |
| `${SegmentInit}` | Initialisation, before any Pre hooks |
| `${SegmentPre}` | Before the primary/secondary split |
| `${SegmentPrePrimary}` | Before the (first) app launch — the most common custom hook: register DLLs, rename files into place, set up extra redirection |
| `${SegmentPreExec}` | Immediately before execution (either instance kind). The manual advises preferring `Pre` |
| `${SegmentPreExecPrimary}` | Immediately before the primary executable is executed |
| `${SegmentPreExecSecondary}` | Immediately before a secondary executable is executed |
| `${SegmentPost}` | Cleanup/restoration for either instance kind |
| `${SegmentPostPrimary}` | After the primary app exits — undo what PrePrimary did (unregister DLLs, rename files back) |
| `${SegmentPreSecondary}` | Before a secondary launch (launcher invoked again while the app is already running) |
| `${SegmentPostSecondary}` | After a secondary launch |
| `${SegmentUnload}` | Final teardown, after all Post hooks |

There is no `PreUnload`/`PostUnload` hook. The execution step itself is
not a hook — it can only be replaced wholesale with `${OverrideExecute}`.

The built-in **segments** these hooks belong to (names used by
`${DisableSegment}`, `${DisableHook}`, and the `DEBUG_SEGMENT_…` flags
in [`08-testing-debugging-troubleshooting.md`](08-testing-debugging-troubleshooting.md)):
`Core`, `DirectoriesCleanup`, `DirectoriesMove`, `DirectoryMoving`,
`DriveLetter`, `Environment`, `ExecString`, `FileWrite`, `FilesMove`,
`InstanceManagement`, `Java`, `Language`, `OperatingSystem`, `Qt`,
`RefreshShellIcons`, `Registry`, `RegistryCleanup`, `RegistryKeys`,
`RegistryValueBackupDelete`, `RegistryValueWrite`, `RunAsAdmin`,
`RunLocally`, `Services` (currently not functional and disabled),
`Settings`, `SplashScreen`, `Temp`, `Variables`, `WorkingDirectory`.

The manual's custom-code page links the exhaustive hook list; if you
need a hook not listed here, look it up there rather than guessing a
name — an unknown `${Segment…}` macro fails the Generator compile, which
is your safety net.

### Worked example — register a DLL only while the app runs

From official forum guidance for a VB6-era app shipping `ccrpbds6.dll`:

```nsh
${SegmentFile}

${SegmentPrePrimary}
    RegDLL $AppDirectory\PIXResizer\ccrpbds6.dll
!macroend

${SegmentPostPrimary}
    UnRegDLL $AppDirectory\PIXResizer\ccrpbds6.dll
!macroend
```

(`$AppDirectory` is a PAL-provided NSIS variable holding the package's
`App` directory path; `$Bits` similarly holds 32/64 for bitness checks in
custom code. These are NSIS variables for custom code — not `%…%` envsub
variables; see docs/06 for the distinction.)

### Worked example — an extra user-config option

Custom code can define new keys for the user configuration file
(`<AppID>.ini` next to the exe) with `${ReadUserConfig}`:

```nsh
${SegmentFile}

${SegmentInit}
    ${ReadUserConfig} $1 AlwaysUse32Bit
    ${If} $1 == true
        StrCpy $Bits 32
    ${EndIf}
!macroend
```

Any key you introduce this way **must be documented in the package's
`help.html`**, and boolean keys use `true`/`false` by convention.

## Reading configuration from custom code

| Macro | Purpose |
|---|---|
| `${ReadLauncherConfig} $0 Section Key` | Read a value from the launcher INI (wraps `ReadINIStr`; check `${Errors}` after `ClearErrors` to distinguish missing from empty) |
| `${ReadLauncherConfigWithDefault} $0 Section Key Default` | Same, with a fallback value when the key does not exist |
| `${ReadUserConfig} $0 KeyName` | Read a value from the user config file next to the exe (renamed from `${ReadUserOverrideConfig}` in 2.1; the Generator upgrades the old name) |

## Defining your own environment variables

```nsh
${SetEnvironmentVariablesPath} VarName $value
```

Defines (or overrides) an environment variable that the rest of the
launcher — including envsub in the launcher INI — can then use as
`%VarName%`. The production pattern (Notepad++ Portable, mirrored in
[`../examples/real-world/notepadplusplus/`](../examples/real-world/notepadplusplus/)):
define a `FullAppDir` variable in `${SegmentInit}` that points at the
32-bit or 64-bit app folder depending on `$Bits`, then use `%FullAppDir%`
as the target throughout `[FilesMove]`/`[DirectoriesMove]`. Remember:
`%FullAppDir%` without a definition like this does nothing — it is not a
built-in (the built-in is `%PAL:FullAppDir%`, the folder of the running
`ProgramExecutable`; see
[`06-environment-variables.md`](06-environment-variables.md)).

## Disabling built-in behaviour (last resort)

```nsh
${DisableHook} Segment Hook     ; disable one hook of a built-in segment
${DisableSegment} Segment        ; disable a whole built-in segment
```

The manual's warning stands: disabling segments very easily breaks the
launcher's backup/restore symmetry and strands user data or host
settings. Ask in the Development forum before doing this.

## Overriding the execute step (last resort)

```nsh
${OverrideExecute}
    ; ... complete replacement for the app-launch step ...
!macroend
```

Only when the standard execution genuinely cannot run the app. Read
PAL's own Execute function first (`Other\Source\PortableApps.comLauncher.nsi`
in the Launcher's source) — an override that forgets argument forwarding
or exit-code handling will fail testing in ways that look like app bugs.

## Debugging custom code and launchers

- **Debug.nsh:** since PAL 2.1, debugging code lives in
  `App\AppInfo\Launcher\Debug.nsh` (previously
  `Other\Source\PortableApps.comLauncherDebug.nsh`; the Generator
  upgrades the path). Debug builds log what each segment does, which is
  how you prove a hook fired and in what order. Regenerate the launcher
  after changing debug code, and do not ship a debug build as a release.
- **MessageBox probes:** the low-tech standard — temporary
  `MessageBox MB_OK "..."` lines in a hook confirm execution and show
  variable values during development.
- **Generator output is the compiler log:** a failed generation prints
  the NSIS error with the file/line of the offending macro or include;
  fix that first error, not the cascade after it.
- A missing `Custom.nsh` include warning at generation time
  (`could not find: "...App\AppInfo\Launcher\Custom.nsh"`) simply means
  the package has no custom code — it is a warning, not a failure, in
  template-based packages that reference the file optionally.

## When custom code is the wrong answer

- The behaviour is expressible in the INI (moves, writes, environment,
  registry) — INI wins: it is validated, documented, and survives PAL
  upgrades.
- You are tempted to write a whole separate NSIS launcher — don't, for
  anything intended for official release; PAL is more powerful, more
  stable, and far easier to maintain (the developers' own guidance).

# 06 — PAL Environment Variable Substitution (envsub)

Source: official PAL 2.2 manual, `ref/envsub.html` and
`topics/languages.html`. Verified 2026-11-16.

Substitution applies to almost every path/string value in the launcher
INI (`[Launch]`, `[Environment]`, `[FileWriteN]`, `[FilesMove]`,
`[DirectoriesMove]`, cleanup sections, `[Language*]`,
`[RegistryValueWrite]`, …). Ordinary Windows environment variables
(`%TEMP%`, `%PATH%`, `%APPDATA%`, …) may also be used; the variables below
are the PAL-provided ones.

## Alternative forms for directory variables

Every **directory** variable below exists in four forms:

| Form | Example |
|---|---|
| `%VAR%` | `X:\PortableApps\AppNamePortable\App` |
| `%VAR:ForwardSlash%` | `X:/PortableApps/AppNamePortable/App` |
| `%VAR:DoubleBackslash%` | `X:\\PortableApps\\AppNamePortable\\App` |
| `%VAR:java.util.prefs%` | java.util.prefs escaping: forward-slash separated, characters other than colon and lower-case letters escaped with `/` |

Partial-directory variables get the same forms. Drive variables do not.
The case of drive/partial-dir variables is not guaranteed (may be upper
or lower case) — never do case-sensitive matching against them.

## Drive variables

| Variable | Meaning |
|---|---|
| `%PAL:Drive%` | Drive letter **with colon** the app runs from, e.g. `X:`. In Live mode this is the portable device location, not the temp copy |
| `%PAL:LastDrive%` | Drive letter with colon from the **previous** run, e.g. `W:` |
| `%PAL:DriveLetter%` | Drive letter **without colon**, e.g. `X`. For patterns like `file:////%PAL:DriveLetter%/`. **Do not use when supporting UNC** — for UNC paths this is `\` |
| `%PAL:LastDriveLetter%` | Previous drive letter without colon. Same UNC caveat |

## Directory variables

| Variable | Meaning |
|---|---|
| `%PAL:AppDir%` | The package's `App` directory, normally `X:\PortableApps\AppNamePortable\App`. In Live mode: `%TEMP%\AppNamePortableLive\App` unless `[LiveMode] CopyApp=false` |
| `%PAL:DataDir%` | The package's `Data` directory, normally `X:\PortableApps\AppNamePortable\Data`. In Live mode: `%TEMP%\AppNamePortableLive\Data` |
| `%JAVA_HOME%` | Only with `[Activate] Java=find` or `require`. The found JRE/JDK root (no trailing `\bin`). With `find` the path may not exist; with `require` the launcher aborts if Java is not found |
| `%PortableApps.comDocuments%` | PortableApps Documents folder, normally `X:\Documents`. Existence not guaranteed |
| `%PortableApps.comPictures%` | Normally `X:\Documents\Pictures`. Existence not guaranteed |
| `%PortableApps.comMusic%` | Normally `X:\Documents\Music`. Existence not guaranteed |
| `%PortableApps.comVideos%` | Normally `X:\Documents\Videos`. Existence not guaranteed |
| `%PAL:PortableAppsDir%` | The `PortableApps` directory — exactly: **the parent directory of the package**, normally `X:\PortableApps` |
| `%PAL:PortableAppsBaseDir%` | Base of the PortableApps hierarchy — the directory that normally contains `PortableAppsDir` and the Documents folder. Note the spelling: `BaseDir`, **not** `BaseDirectory` |
| `%PAL:LastPortableAppsBaseDir%` | Previous run's `%PAL:PortableAppsBaseDir%` |
| `%USERPROFILE%` | Host user profile, e.g. `C:\Users\Username` |
| `%ALLUSERSPROFILE%` | All-users profile, e.g. `C:\ProgramData` (Vista+). See `%ALLUSERSAPPDATA%` below — most apps should use that instead |
| `%ALLUSERSAPPDATA%` | **Invented by PAL** (does not exist in Windows itself; new in 2.1). Like `ALLUSERSPROFILE` but on 2000/XP it appends `\Application Data`. On Vista+: `C:\ProgramData` |
| `%LOCALAPPDATA%` | e.g. `C:\Users\Username\AppData\Local` |
| `%APPDATA%` | e.g. `C:\Users\Username\AppData\Roaming` |
| `%DOCUMENTS%` | The **host** Documents folder, e.g. `C:\Users\Username\Documents` — distinct from `%PortableApps.comDocuments%` |
| `%TEMP%` | The temp directory the app will see — if `[Launch] CleanTemp` assigned a contained temp dir, this is that dir |

## Partial directory variables

For updating paths stored inside settings files when the package moves
(used with `[FileWriteN] Type=Replace`):

| Variable | Meaning |
|---|---|
| `%PAL:PackagePartialDir%` | Current package path **minus drive letter and colon**, e.g. `\PortableApps\AppNamePortable` |
| `%PAL:LastPackagePartialDir%` | Same, for the previous run, e.g. `\Apps\AppNamePortable`. On first run it equals `PackagePartialDir`, so a Find/Replace pair using both is skipped |

Typical use:

```ini
[FileWrite1]
Type=Replace
File=%PAL:DataDir%\settings\app.conf
Find=%PAL:LastPackagePartialDir%
Replace=%PAL:PackagePartialDir%
```

## Language variables

Set by the PortableApps.com Platform when it launches the app (values
shown for English / Portuguese / Brazilian Portuguese):

| Variable | Examples |
|---|---|
| `%PortableApps.comLanguageCode%` | `en`, `pt`, `pt-br` |
| `%PortableApps.comLocaleCode2%` | `en`, `pt`, `pt` |
| `%PortableApps.comLocaleCode3%` | `eng`, `por`, `por` |
| `%PortableApps.comLocaleglibc%` | `en_US`, `pt`, `pt_BR` (exact spelling: `Localeglibc`) |
| `%PortableApps.comLocaleID%` | `1033`, `2070`, `1046` |
| `%PortableApps.comLocaleWinName%` | `LANG_ENGLISH`, `LANG_PORTUGUESE`, `LANG_PORTUGUESEBR` |
| `%PortableApps.comLocaleName%` | `English`, `Portuguese`, `PortugueseBR` |
| `%PAL:LanguageCustom%` | Custom value built by `[Language]` + `[LanguageStrings]` (+ `[LanguageFile]`) in the launcher INI |

## Production-verified, but missing from the manual's envsub page

These do **not** appear in the PAL 2.2 manual's `envsub` page, but are used
by official production packages in
[AppConfigs](../examples/real-world/README.md) — treat them as real:

- `%PAL:FullAppDir%` — the directory of the running `ProgramExecutable`
  under `App\` (32/64-bit aware). Used by 7-Zip Portable, e.g.
  `CheckIfExists=%PAL:FullAppDir%\Lang\%PAL:LanguageCustom%.txt`.
- `%PAL:DriveHex%` / `%PAL:LastDriveHex%` — the drive letter in the hex
  form used inside `REG_BINARY` data in `.reg` files. 7-Zip Portable
  patches them with a `[FileWriteN]` pair:
  `Find=%PAL:LastDriveHex%,00,3a,00` → `Replace=%PAL:DriveHex%,00,3a,00`.

Related trap: `%FullAppDir%` **without** the `PAL:` prefix is **not** a
built-in. Notepad++ Portable defines its own in `Custom.nsh`
(`${SetEnvironmentVariablesPath} FullAppDir …` in `${SegmentInit}`,
choosing the 32/64-bit folder via `$Bits`). If you see `%FullAppDir%` in a
config, check its `Custom.nsh` for the definition — and if you copy the
pattern, copy the definition too
([05-launcher-advanced-custom-code.md](05-launcher-advanced-custom-code.md)).

## Not real (do not use)

Verified **absent** from the PAL 2.2 manual — commonly hallucinated or
from forum proposals:

- `%PAL:BinDir%` — does not exist in 2.2.
- `%PAL:PortableAppsBaseDirectory%` — wrong name; use `%PAL:PortableAppsBaseDir%`.
- `%PortableApps.comLanguage%` — not a variable; use the `…LanguageCode%` / locale variables above.
- `%PAL:Bits%` — not an envsub variable; `$Bits` is an NSIS variable for
  custom code only.
- `%PAL:CurrentDrive%` — appears once in a manual example but is not
  defined; use `%PAL:Drive%`.

# 07 — End-to-End Workflow: From Local App to .paf.exe

This is the complete procedure for packaging an existing Windows
application as a PortableApps.com Format package. Follow it in order.

## Phase 0 — Legality and feasibility check

1. Confirm you may package the app (see
   `docs/09-licensing-permissions-submission.md`): open source → check the
   license; freeware → publisher or publisher's written consent only;
   commercial → do not proceed without an agreement.
2. Confirm the app *can* be portable: it must not require a kernel driver,
   a Windows service that cannot be started/stopped portably, or machine
   activation tied to hardware IDs. Apps needing admin rights must declare
   `RequiresAdmin=yes` in `appinfo.ini`.
3. Get the official tools (`docs/11-tools-and-versions.md`):
   PortableApps.com Launcher, PortableApps.com Installer, and the
   PortableApps.com Application Template (commented reference configs).

## Phase 1 — Analyse the base app (find every trace)

Work in a **clean** environment: a fresh Windows VM, Windows Sandbox, or a
snapshot you can revert. Never analyse on a machine where the app was
previously installed — leftover traces corrupt the results.

1. Snapshot the clean system: registry + file system. **RegShot** is the
   classic tool: take Shot 1.
2. Install the app the normal way (or, if it ships as an archive, extract
   it). Note the install directory and every option the installer offers.
3. Run the app. Change every setting. Create data. Use every major
   feature. Close the app.
4. Take Shot 2 and compare. Record:
   - Registry keys/values created or changed (usually under
     `HKCU\Software\<Publisher>\<App>`, sometimes `HKLM`).
   - Files/folders created or changed: `%APPDATA%`, `%LOCALAPPDATA%`,
     `%USERPROFILE%`, Documents, the install folder itself.
   - Any files written *outside* those (temp files are usually ignorable;
     settings are not).
5. Also test: does the app store paths inside its settings (absolute paths
   break when the drive letter changes)? Does it have a "portable mode"
   switch, a `-portable` flag, or a settings-file-next-to-exe mode? A
   native portable mode always beats launcher redirection.
6. Revert the snapshot. You now have the app's **trace inventory** — every
   item on it must be handled by the launcher or consciously accepted.

## Phase 2 — Lay out the package

1. Copy `templates/MinimalAppPortable/` and rename to `<AppName>Portable`.
2. Put the app's binaries in `App\<AppName>\` (from the local install or
   extracted archive). Remove uninstallers and anything that only serves
   the local installer.
3. Put first-run default settings in `App\DefaultData\` (mirroring the
   structure they should have in `Data\`).
4. Leave `Data\` empty in the distributed package (a placeholder file is
   fine); the launcher populates it from `DefaultData` on first run.
5. Write `help.html` and `Other\Source\Readme.txt` (launcher readme —
   model it on the template in `templates/`).

## Phase 3 — appinfo.ini

Fill in `App\AppInfo\appinfo.ini` from `docs/01-format-spec.md`:

- `[Format] Version=3.9`
- `AppID` = folder name; `Category` from the fixed list of 10;
  `Description` ≤ 512 chars; no double quotes anywhere.
- `[License]` booleans that are *true for this app*.
- `PackageVersion` = app version padded to 4 parts, 4th part = packaging
  revision starting at 1 for a first packaging of that app version
  (convention: app `2.4.4` → `2.4.4.1`).
- `[Dependencies]` for Java/.NET/Ghostscript/64-bit/admin requirements.
- `[Control] Start=<AppID>.exe`; `BaseAppID` (or `NOT-NEEDED`).
- Add the icon set (`appicon.ico` + 5 PNGs) to `App\AppInfo`.

## Phase 4 — launcher.ini

Write `App\AppInfo\Launcher\<AppID>.ini` using
`docs/04-launcher-ini-reference.md`. Map every item from the trace
inventory:

| Trace found | Launcher mechanism |
|---|---|
| Settings in `HKCU\Software\...` | `[Activate] Registry=true` + `[RegistryKeys]` (+ cleanup sections) |
| Settings in `%APPDATA%\App` | `[DirectoriesMove]` or `[FilesMove]` to `%PAL:DataDir%` |
| Single settings file anywhere | `[FilesMove]` |
| App reads a path from a config file | `[FileWriteN]` to rewrite it each launch with `%PAL:DataDir%` |
| App needs an environment variable | `[Environment]` |
| App stores settings in its own folder | Point it at `Data` via its own portable switch if any; otherwise move the settings file with `[FilesMove]` |
| App is Java-based | `[Activate] Java=find` or `Java=require` (finds Java Portable / local Java; `yes` is not a valid value) |
| App is a Qt app writing to registry | `[QtKeysCleanup]` + `[RegistryKeys]` (there is no `[Qt]` section in PAL 2.2 — see `docs/04-launcher-ini-reference.md`) |
| Local copy of same app exists on host | PAL backs up host settings and restores them on exit automatically for the keys/files it manages — verify in testing |

Start from the closest file in `examples/`. Keep the INI minimal: only
sections the app actually needs.

## Phase 5 — Generate the launcher

1. Install/extract the PortableApps.com Launcher package; run
   `PortableApps.comLauncherGenerator.exe` (the Generator).
2. Point it at the package folder (`<AppName>Portable`).
3. It reads `App\AppInfo\Launcher\<AppID>.ini`, validates it, and compiles
   `<AppID>.exe` into the package root using NSIS. Prerequisite
   (`docs/03-launcher-overview.md`): NSIS Portable (**Unicode** variant)
   installed as the sibling folder `NSISPortable` next to
   `PortableApps.comLauncher` — the ANSI variant is not used.
4. Fix every Generator error before continuing. The
   `!include: could not find` warnings for the optional `Custom.nsh` /
   `Debug.nsh` files are harmless when those files are intentionally
   absent (`docs/08-testing-debugging-troubleshooting.md`); any other
   warning about missing files or bad keys means the launcher is not
   done.

## Phase 6 — Test the package folder (before building the installer)

Run the full test matrix in
`docs/08-testing-debugging-troubleshooting.md`. Minimum:

- First run from the folder: defaults appear, app works.
- Change settings, close, reopen: settings persist.
- Copy the folder to a different drive letter / path with spaces and a
  non-ASCII folder name: still works, settings intact.
- Run on a machine (VM) with a **local install of the same app**: local
  settings are untouched after the portable run; portable settings are
  untouched by the local app.
- Exit cleanliness: snapshot registry + file system before/after a full
  run — no leftovers outside the package folder.
- Run as a limited (non-admin) user.
- Run twice / run while already running (single-instance behaviour).

## Phase 7 — installer.ini (only if needed)

Defaults cover most apps. Write `App\AppInfo\installer.ini` only for:
online downloads (`[DownloadFiles]`), optional components, upgrade
preservation/removal tweaks, local-copy import (`[CopyLocalFiles]`), or
legacy-version handling. See `docs/02-installer-and-installer-ini.md`.

## Phase 8 — Build the .paf.exe

1. Run `PortableApps.comInstaller.exe`, point it at the package folder.
2. Output: `<AppID>_<DisplayVersion>.paf.exe` next to the package folder
   (online: `..._online.paf.exe`).
3. Record the Installer version used; confirm it is current (≤30 days
   superseded rule).

## Phase 9 — Test the built installer

1. Install the `.paf.exe` to a **fresh** `PortableApps` folder (ideally a
   different VM/drive than the build tree).
2. Repeat the Phase 6 matrix against the *installed* copy.
3. Upgrade test: install the previous package version, create settings,
   install the new `.paf.exe` over it — settings survive, old binaries
   are gone, `Data` intact.
4. Uninstall expectation: deleting the folder removes everything (there
   is no separate uninstaller; the folder *is* the app).

## Phase 10 — Release

1. Complete `checklists/pre-release-checklist.md`.
2. Name the file exactly `<AppID>_<DisplayVersion>.paf.exe`.
3. Publish with a changelog entry stating the base app version and the
   packaging revision (DisplayVersion), e.g. "2.4 Revision 1".
4. For PortableApps.com publication, post a Development Test release in
   the Portable App Development forum and iterate; see
   `docs/09-licensing-permissions-submission.md`.

# 08 — Testing, Debugging, and Troubleshooting

## The test matrix

Test the **extracted/installed package**, never just the build tree, and
test a fresh copy for each "first run" item (delete `Data` contents
between first-run tests).

### First run and persistence

- [ ] First launch: `Data` is populated from `App\DefaultData`; the app
      starts with sane defaults.
- [ ] Change every category of setting (options, window size, recent
      files, language); close; relaunch: all persist.
- [ ] Create user data inside the app (documents, profiles, playlists):
      it lands inside `Data`, not in `App` and not on the host.
- [ ] Delete the `Data` folder entirely: the app recreates it and starts
      cleanly (Format requirement).

### Portability

- [ ] Copy the package to a different drive letter: settings, MRU lists,
      and language survive; no "file not found" for internal paths.
- [ ] Run from a path containing spaces and from a path containing
      non-ASCII characters.
- [ ] Run from a read-only location with `RunLocally` (user config): the
      launcher copies to a temp folder and runs from there.
- [ ] Run via UNC path if `[Launch] SupportsUNC` is claimed.
- [ ] Limited (non-admin) Windows user account: full functionality unless
      the app itself needs admin.

### Host cleanliness (the leak test)

1. On a clean VM/snapshot, record registry + file state (RegShot Shot 1).
2. Run the portable app, use it, close it, wait for the launcher to exit
   fully (check Task Manager — the launcher waits for child processes).
3. Shot 2 + compare: **zero** new/changed keys or files attributable to
   the app outside the package folder. Temp files the app creates and
   Windows itself creates (Prefetch, etc.) are OS noise; settings,
   caches with user data, and registry keys are leaks.
4. Repeat with a **locally installed copy of the same app present**:
   before the portable run, set a distinctive value in the local copy's
   settings; after the portable run, the local value must be intact and
   the portable run must not have read it.

### Lifecycle

- [ ] Launch while the app is already running: behaviour matches
      `[Launch] SingleAppInstance` / `SinglePortableAppInstance` intent
      (second launch passes the file/argument to the running instance or
      is refused cleanly — never a corrupted settings file).
- [ ] Open a file via the Platform / Explorer "Open With" / drag-and-drop
      onto the launcher exe: the app opens that file (argument passing).
- [ ] Close the app via its own exit path and via closing the launcher's
      watched EXE: cleanup still happens.
- [ ] Crash the app (kill the process): on next launch the launcher
      recovers (it detects the unclean exit and restores backups).
- [ ] Eject/remove the drive while running is *not* a supported scenario;
      but a forced launcher kill must not corrupt `Data`.

### Installer

- [ ] Fresh install of the `.paf.exe` to an empty `PortableApps` folder.
- [ ] Install while the app is running: installer detects it
      (`[CheckRunning]`) and offers to close it.
- [ ] Upgrade over the previous version: settings preserved, replaced
      binaries actually replaced, removed files actually removed
      (`[FilesToRemove]`/preservation rules honoured).
- [ ] Online installer: download verifies against `DownloadSHA256`;
      a tampered/wrong download fails loudly, not silently.
- [ ] Install to a path with spaces; install when the target drive is
      nearly full (installer must refuse cleanly).

### Contexts (add the rows that match what help.html claims)

- [ ] Cloud folder: package inside a synced folder (OneDrive/Dropbox/
      Google Drive), sync client running; run on machine A, let it sync,
      run on machine B: settings intact, no sync-conflict copies inside
      `Data`. (PAL behaviour under sync clients is **Unverified** —
      record what you observe.)
- [ ] Second Windows user account on the same PC: the portable run does
      not read or alter the other account's local settings.
- [ ] Deep path: install under a folder path of 200+ characters; first
      run, persistence, and Live mode all work.
- [ ] Non-English Windows image (if multilingual is claimed): installer
      language, app language via the Platform, and the `[LanguageFile]`
      fallback when launched directly all behave.
- [ ] Policy-realistic account: standard user, no elevation available;
      every non-admin feature works, admin features refuse cleanly.
- [ ] Offline: with networking disabled, a full installer installs and
      runs; an online installer fails with a clear message and leaves no
      half-installed package. (Expected online-installer failure
      behaviour: **Unverified** — record what you actually observe.)
- [ ] Keyboard-only pass: installer, splash dismissal, and first run
      completed without a mouse (`docs/19-accessibility.md`).
- [ ] (Optional, community packages) Wine: the package installs and runs
      under Wine. Not an official-format requirement.

## Debugging the launcher

- **PAL debug builds:** put debug flags in
  `App\AppInfo\Launcher\Debug.nsh` (PAL 2.1+ location; see
  `docs/05-launcher-advanced-custom-code.md`) and regenerate — the
  Generator finds the file and compiles debugging in. Debug output goes
  to message boxes **and to `Data\debug.log`** in the package. Debugging
  is compile-time only; there is no runtime debug switch. **Remove
  `Debug.nsh` for release builds** or users get a debug build.

  | Flag in Debug.nsh | Effect |
  |---|---|
  | `!define DEBUG_ALL` | Debug almost everything (`DEBUG_GLOBAL` + all segment flags; segment announcements still need `DEBUG_SEGWRAP`) |
  | `!define DEBUG_GLOBAL` | Debug code outside all segments |
  | `!define DEBUG_SEGMENT_<SegmentName>` | Debug one segment, e.g. `DEBUG_SEGMENT_RunAsAdmin` (segment names in `docs/05…`) |
  | `!define DEBUG_SEGWRAP` | Announce each segment as it starts/finishes ("About to execute segment" / "Finished executing segment") |
  | `!define DEBUG_OUTPUT file` | Output to `Data\debug.log` only. `messagebox` = boxes only. Default (unset) = both; any other value silences output |

- **Harmless Generator warnings:** `!include: could not find:
  "…\Other\Source\PortableApps.comLauncherCustom.nsh"` (and the same for
  `…LauncherDebug.nsh`) are **warnings, not errors** — they simply mean
  the package has no custom code / no debug code. Do not create empty
  files to silence them.
- **Bisect the INI:** comment out half the move/registry entries, retest,
  narrow down. Launcher problems are almost always one bad entry.
- **Watch live:** Process Monitor (ProcMon) filtered to the app process
  shows every file/registry access in real time — the fastest way to find
  a settings location the RegShot pass missed (e.g. writes that only
  happen on a specific feature).
- **Check the wait chain:** if cleanup does not happen, the app probably
  spawned a child process that outlives the main EXE. Use
  `[Launch] WaitForEXE1`… (see the launcher reference) so the launcher
  waits for the real worker process.

## Common problems and fixes

| Symptom | Likely cause | Fix |
|---|---|---|
| Settings reset every run | Settings location not captured; app writes to `%APPDATA%` or registry that is never moved | Find the real location (ProcMon/RegShot), add `[FilesMove]`/`[DirectoriesMove]`/`[RegistryKeys]` |
| Settings reset only when drive letter changes | App stores absolute paths in its settings file | `[FileWriteN]` to rewrite the path on each launch with `%PAL:DataDir%` etc. |
| Local install's settings changed after portable run | Launcher key/file overlaps the local app's, backup/restore missing or the app was already running locally | Ensure the same entries are in the backup-managed sections; never run both copies at once |
| Registry key left behind after exit | Key created by the app but not listed, or a parent key not cleaned | Add the key to `[RegistryKeys]`; add empty parents to `[RegistryCleanupIfEmpty]` |
| Empty folders left in `%APPDATA%` | Directory moved back but source shell left | `[DirectoriesCleanupIfEmpty]` / `[DirectoriesCleanupForce]` |
| "Another instance is running" on first launch | Stale lock from a crashed run, or `SingleAppInstance` mismatch | Check the app's lock file location (move it to `Data`); verify `[Launch]` instance settings |
| Launcher exits immediately, app never starts | Wrong `ProgramExecutable` path (relative to `App\`), or missing runtime (Java/.NET) | Verify the path; add `[Activate] Java` / `UsesDotNetVersion` as applicable; check debug log |
| "*…Portable did not close properly last time it was run and will now clean up*" on launch | Previous run ended without cleanup (crash, unsafe USB eject, Windows shutdown with the app open) — the launcher could not restore local data then | Expected recovery behaviour, not a package bug; launch again after cleanup. If it recurs every run, the app is crashing or a child process holds files open |
| "*…Cannot be started… (ERROR: App\<path>.exe could not be found)*" | `ProgramExecutable` names a file that is not in the package at that relative path | Fix `[Launch] ProgramExecutable` (it is relative to `App\`) and regenerate |
| App starts but can't find its DLLs/plugins | Working directory wrong, or plugin dir moved | Set `[Launch] WorkingDirectory` (sparingly) or keep plugins in `App` and exclude via `[SpecialPaths] Plugins` |
| Second launch loses the file it was asked to open | App's single-instance forwarding + launcher argument order | Review `CommandLineArguments` and the app's own forwarding; test open-with explicitly |
| Installer refuses / hash mismatch on online install | Publisher changed the download, or wrong hash recorded | Re-download from the publisher, verify manually, update `DownloadSHA256` deliberately |
| Upgrade wipes user settings | `installer.ini` removes `Data`, or `DefaultData` overwrites on upgrade | `RemoveDataDirectory` must stay false/omitted; check `[DirectoriesToPreserve]` |
| Menu shows wrong/no icon | Missing PNG size or malformed ICO | Provide the full icon set per `docs/01-format-spec.md` §3 |
| Platform offers no update | `PackageVersion` not increased, or not 4-part numeric | Fix `[Version] PackageVersion` |
| App fails on Windows XP/7-era system | MinOS not declared / runtime too new | Set `[Launch] MinOS` in the launcher INI and test on the oldest claimed OS |

## Performance sanity

- Launcher startup should add well under a second for typical apps.
  Registry/file moves of huge directories (browser profiles) are the
  usual cost — prefer in-place redirection (environment variables,
  command-line switches, the app's own portable mode) over moving large
  trees when the app supports it.
- Avoid `WaitForProgram=false` unless the app truly forks and exits;
  cleanup correctness beats shaving milliseconds.

# 09 — Licensing, Permissions, and Submitting to PortableApps.com

## The Format's permissions rule (§7 of the Format specification)

> Applications packaged in PortableApps.com Format using our tools must
> be done in accordance with local and international law. **Freeware may
> be packaged using the PortableApps.com Installer but only if the
> installer is unmodified and in its original form** as distributed by
> PortableApps.com. **Freeware may only be packaged by the original
> publisher or with the express consent of the publisher.** Commercial
> software may be packaged by contacting PortableApps.com.

Practical consequences:

- **Open source apps** (OSI-approved license): packaging is permitted by
  the license; still honour trademark rules (below) and include the
  license + source offer in `Other\Source` as the license requires.
- **Freeware (closed source, free of charge)**: you need to *be* the
  publisher or have the publisher's express consent. "It's free" is not
  consent to redistribute. If consent covers distribution but not
  modification/repackaging of the download, use an **online installer**
  (`[DownloadFiles]`) so the bits come from the publisher at install time.
- **Commercial/shareware**: do not package without an agreement with the
  publisher / PortableApps.com.
- **Your own app**: no restriction beyond the tool licenses.

## License metadata must match reality

The `[License]` section of `appinfo.ini` (`Shareable`, `OpenSource`,
`Freeware`, `CommercialUse`) is shown to users in the Platform and drives
distribution decisions. Setting `OpenSource=true` for a freeware binary,
or `Shareable=true` for an app whose license forbids redistribution, is a
defect as real as a broken launcher.

## Trademarks and naming

- The `AppID`/name rules in `docs/01-format-spec.md` exist partly for
  trademark safety: third-party packages carry a suffix
  (`AppNamePortable-example.com` / `AppNamePortable-username`) so they are
  not mistaken for official releases.
- Record trademark notices in `[Details] Trademarks`.
- `BaseAppName` / `ExtractIcon` / `ExtractName` exist for cases where the
  law requires the base app's own name/icon to be used — only then.

## What goes in the package

- The base app's license file(s) and any required notices — normally in
  `App\<AppName>` (as shipped) and/or `Other\Source`.
- If the app is open source, the corresponding source code or a written
  offer/link per its license; PortableApps.com packages conventionally
  note source availability in `Other\Source\Readme.txt` and `help.html`.
- The launcher's own readme (`Other\Source\Readme.txt`, from the
  template) states that the installer and launcher are GPL and where
  their source is available — keep that text intact in derived packages.
- A EULA that must be accepted at install time goes in
  `App\AppInfo\EULA.txt` (see `docs/02-installer-and-installer-ini.md`).

## Development Test releases and official publication

PortableApps.com's community process (via the Portable App Development
forum at portableapps.com):

1. Build and self-test the package thoroughly first
   (`docs/08-testing-debugging-troubleshooting.md`). Do not post a
   package you have not run.
2. Post it as a **Development Test (DT)** release in the Beta Testing
   forum (per the forum's Development Test posting layout): subject
   pattern is the app name + version + "Development Test" revision
   (e.g. "AppName Portable 1.2 Development Test 1"). Include:
   what the app is, its license status and your permission to package it,
   the download link to the `.paf.exe`, its MD5/SHA hash, and known
   issues. Then note the release on the Development Test Releases page,
   and edit the original post for updates rather than starting new
   threads. DT-specific rules:
   - The DT installer file is named with the Dev Test pattern:
     `AppNamePortable_1.2_Dev_Test_1_English.paf.exe`.
   - Compile the **Development Test splash screen** (from the
     Application Template) into the launcher, so testers can see the
     build is not a final release.
   - Follow the current Format specification and build with the current
     Installer — DTs are held to the same format rules as releases.
3. Community members test on varied Windows versions and report leaks,
   leftovers, and bugs. Fix, increment the DT number, repost.
4. When a DT is clean, it becomes a candidate for an official release
   ("Apps Ready For Official Release" tracking). Posting there is a
   commitment: only the app's author/packager may post it, and you must
   be willing to **support the app on an ongoing basis (at least
   6 months)**. Official releases are
   published by PortableApps.com under the app's page, are built with the
   then-current Installer, and thereafter updated through the Platform's
   app store.
5. Keep `PackageVersion` discipline through DTs: DTs are still public
   releases of the package, so `PackageVersion` must increase
   monotonically and stay 4-part numeric (encode test builds in the 4th
   part and in `DisplayVersion`, e.g. DisplayVersion `1.2 Development
   Test 1`).

Rules of thumb from the community process:

- One app per thread; update the first post as DTs progress.
- Respond to tester reports — an unmaintained DT is abandoned, not
  promoted.
- If the base app updates, the portable package is expected to follow;
  stale packages get flagged in the "Outdated Official Apps" tracking.

## Downstream redistribution

Others will copy your package — mirror sites, USB-stick images,
friends. The Format's signals for that are the `[License]` booleans in
`appinfo.ini` (`docs/01-format-spec.md`): `Shareable=true` is the
redistribution signal, and redistributors rely on the booleans being
*accurate* — one more reason false license metadata is a release
defect, not a detail.

- A redistributed copy should be the **unmodified `.paf.exe`**. Anyone
  who re-zips an extracted folder and re-shares it has broken the chain
  of custody the hash discipline depends on
  (`docs/18-security-privacy-and-abuse.md`).
- Copying a package drive-to-drive means copying it **without** the
  `Data` folder — `Data` is the previous user's settings and possibly
  credentials, never part of the distribution.
- Where redistribution of the app itself is not permitted, the online
  installer form is what keeps the publisher's bits out of the
  redistributed file entirely: the `.paf.exe` carries only the downloader
  and the pinned hash.

# 10 — PortableApps.com Platform Integration

How the PortableApps.com Platform (the menu/app store that users run from
`StartPortableApps.exe`) interacts with a package — i.e. what your
`appinfo.ini` values actually *do* on a user's machine.

## Discovery

- The Platform scans its `PortableApps` directory for folders containing
  `App\AppInfo\appinfo.ini`. A package that is not under a `PortableApps`
  folder, or whose `appinfo.ini` is malformed, simply does not appear.
- The menu entry shows `[Details] Name`, the icon set from `App\AppInfo`,
  and `[Control] Start` is what gets executed. Multi-icon apps
  (`Icons=2` + `Start1`/`Name1`…) get multiple menu entries.
- "Refresh App Icons" in the Platform re-scans after manual changes.

## App Store, installs, and updates

- The built-in App Store installs `.paf.exe` files silently through the
  PortableApps.com Installer: the user picks a parent location, the
  package lands in `<PortableApps>\<AppID>`.
- Updates are driven **solely** by comparing the installed
  `[Version] PackageVersion` (4-part numeric) with the store's — a
  package whose `PackageVersion` did not increase will never be offered
  as an update, and a malformed one breaks comparison.
- `InstallType` (and the installer's optional-components writing of it)
  is displayed in the app details so users can tell editions apart
  (e.g. Multilingual vs English).
- `[Dependencies]` values are surfaced/enforced by the Platform:
  `UsesJava=yes` ties the app to Java Portable (jPortable, installed
  under `CommonFiles\Java`); `UsesDotNetVersion` warns/blocks on machines
  lacking the framework; `Requires64bitOS=yes` hides/blocks the app on
  32-bit systems; `RequiresAdmin=yes` marks the app as needing elevation.
- Cached online-installer downloads: when `[DownloadFiles]
  DownloadCachedByPAc` is set, the Platform's store can serve the
  publisher download from the PortableApps.com cache during installs and
  updates.

## Launching from the Platform

- The Platform sets the language environment variables
  (`%PortableApps.comLanguageCode%`, `%PortableApps.comLocale*%` — see
  `docs/06-environment-variables.md`) before starting the launcher, which
  is how `[Language]`/`[LanguageStrings]` in the launcher INI and
  multilingual apps pick their UI language. Outside the Platform those
  variables are absent — that is what `[LanguageFile]` is for.
- File-association features (the Platform's file associations /
  "open with" integration) use `[Associations]` and `[FileTypeIcons]`
  from `appinfo.ini`: `FileTypes`, `Protocols`, and the command-line
  patterns tell the Platform how to pass a file/URL to your launcher.
- A well-behaved package does **not** permanently register file
  associations on the host: association is a Platform feature, and when
  the app itself registers associations, PAL's registry backup/restore
  is the mechanism — the host must end the run as it began (the
  host-modification rule, `docs/01-format-spec.md`).
- `BaseAppID`/`BaseAppID64`/`BaseAppIDARM64` let Platform 16+ create a
  correctly-pinnable taskbar shortcut for the running base app.
- The Platform's "disable splash screens" option works because PAL
  honours it (same mechanism as the user config's `DisableSplashScreen`).

## PortableApps directory conventions

A standard portable drive layout:

```
X:\
  StartPortableApps.exe        (Platform launcher, at drive root)
  PortableApps\
    PortableApps.com\          (the Platform itself)
    CommonFiles\               (shared components: Java, etc.)
    AppNamePortable\           (your package)
  Documents\                   (PortableApps Documents: Music/Pictures/Videos)
```

This is why `%PAL:PortableAppsDir%` is defined as the package's parent
directory and `%PAL:PortableAppsBaseDir%` as the drive-level root, and
why packages must never assume a drive letter or that the parent folder
is literally named `PortableApps` on every machine — use the variables.

## Plugin and CommonFiles installs

Plugin installers (see `docs/02-installer-and-installer-ini.md`) install
*into* an existing package folder from the Platform/manual install flow.
CommonFiles installers target `PortableApps\CommonFiles\<AppID>` and are
reserved for shared components designated by PortableApps.com (Java is
the canonical example).

- Launcher: `App\AppInfo\Launcher\Custom.nsh` (PAL 2.1+; in PAL 2.0 it

- Installer: `Other\Source\PortableApps.comInstallerCustom.nsh`

See `docs/05-launcher-advanced-custom-code.md` and
`docs/02-installer-and-installer-ini.md`.

### Analysis tools (not PortableApps.com products)

- **RegShot** — registry/filesystem before-after snapshots; the standard
  trace-inventory tool.
- **Process Monitor (ProcMon)**, Sysinternals — live file/registry

- **7-Zip** — used by the Installer itself for AdvancedExtract; also the
  manual way to inspect what an upstream installer/archive contains.
- A clean **Windows VM or Windows Sandbox** (Pro/Enterprise/Education;
  not Home) — the analysis environment. Snapshot before, revert after.

## Driving the tools non-interactively

- Both the Generator and the Installer accept the portable app's main
  directory as their target (command line or Windows Send To) — that is
  how you point them at `X:\PortableApps\FileZillaPortable` without
  browsing.
- The scriptable surface for *testing* is the built `.paf.exe`: silent
  installs and the `/DESTINATION=`-style override
  ([`02-installer-and-installer-ini.md`](02-installer-and-installer-ini.md))
  are what the Platform itself uses. Exact switch syntax is
  tool-version-specific — verify against the installed tool's own
  documentation before scripting against it (**Unverified** in this
  repo).

## Automation reality check

- There is **no documented headless mode** for the stock Generator or
  Installer wizard in the sources this repo is built on. Treat launcher
  generation and `.paf.exe` compilation as interactive Windows steps
  unless you have verified otherwise on your exact tool version.
- What *is* automatable today: silent `.paf.exe` install testing;
  INI linting against [`01`](01-format-spec.md) /
  [`02`](02-installer-and-installer-ini.md) /
  [`04`](04-launcher-ini-reference.md) (unknown key, bad `PackageVersion`
  shape, missing required sections); and the unofficial uroesch
  Wine/Docker pipeline for community packages
  ([`13`](13-ecosystem-and-source-repositories.md)).
- A pragmatic CI shape: lint the INIs on any runner, build on a Windows
  runner with a human-triggered release step, and never let CI publish a
  `.paf.exe` no human has installed once.

# 12 — Glossary and FAQ

## Glossary

- **AppID** — Globally unique identifier of a package; also its folder
  name (`AppNamePortable`).
- **appinfo.ini** — `App\AppInfo\appinfo.ini`; metadata the Platform and
  Installer read (name, version, category, license, dependencies).
- **Application Template** — Official skeleton package with commented
  configuration files; the canonical starting point.
- **Base app** — The original, non-portable application being packaged.
- **CommonFiles** — `PortableApps\CommonFiles`; shared components (Java)
  used by multiple packages; also a plugin-installer type.
- **Data directory** — The package's `Data\` folder; the only place user
  data and settings may live.
- **DefaultData** — `App\DefaultData`; first-run defaults copied into
  `Data` by the launcher.
- **Development Test (DT)** — A public test build posted in the Portable
  App Development forum before official release.
- **DisplayVersion** — Human version string (`2.4 Revision 2`); never
  used for update comparison.
- **envsub** — PAL's environment-variable substitution (`%PAL:DataDir%`
  etc.) applied to launcher INI values.
- **Format** — PortableApps.com Format, the layout/behaviour
  specification (current: 3.9).
- **help.html** — The package's help file, in the package root.
- **installer.ini** — Optional `App\AppInfo\installer.ini` configuring
  the PortableApps.com Installer (downloads, optional components,
  upgrade rules).
- **Launcher (PAL)** — PortableApps.com Launcher; the generator + the
  generated `<AppID>.exe` that makes the base app portable.
- **launcher.ini** — Shorthand for `App\AppInfo\Launcher\<AppID>.ini`,
  PAL's configuration file. (The file is never actually named
  `launcher.ini`.)
- **Live mode** — Running from read-only media by copying app/data to a
  temp folder first; forced by the user config `RunLocally=true`.
- **Online installer** — A `.paf.exe` (named `..._online.paf.exe`) that
  downloads the base app at install time via `[DownloadFiles]`.
- **PackageVersion** — 4-part numeric package version (`x.x.x.x`) in
  `appinfo.ini`; drives update checks.
- **.paf.exe** — A compiled PortableApps.com Format installer file.
- **PAL** — PortableApps.com Launcher.
- **Platform** — The PortableApps.com Platform: menu, App Store, updater.
- **Plugin installer** — A `.paf.exe` built from `plugininstaller.ini`
  that adds files to an existing package.
- **RegShot** — Snapshot/compare tool used to discover an app's traces.
- **Segment** — A named hook block in PAL custom NSIS code that runs at a
  specific point in the launcher lifecycle.
- **Trace inventory** — The complete list of registry keys/files an app
  touches, gathered during analysis; every item must be handled by the
  launcher.

## Easily confused — five different things called "portable"

| Thing | What it actually is |
|---|---|
| A Format package (folder) | The extracted `AppNamePortable` tree: `App\`, `Data\`, `Other\`, the generated launcher exe, help.html. What the packager authors and what actually runs |
| A `.paf.exe` | The compiled installer that *delivers* a Format package. It is an artifact of the package, not the package itself |
| A ZIP of the package folder | The same tree in an archive. Works when extracted by hand, but no App Store install/update, no validation — not a Format release (see the FAQ below) |
| A "portable by design" app | A base app that natively keeps its settings beside its exe. It still needs a Format package (metadata, launcher, installer) to be a PortableApps.com release |
| The Platform | The menu/App Store program that discovers, installs, updates, and launches packages. Packages must also work launched directly, without it |

## FAQ

**Do I need to write code to make a portable app?**
Usually not. Most apps are made portable with only the launcher INI.
NSIS custom code is the escape hatch for the rest.

**Can I just zip the folder instead of building a .paf.exe?**
A zipped package folder works when extracted manually, but it is not a
PortableApps.com Format *release*: no App Store install/update, no
upgrade preservation rules, no online-download mechanism. Official-style
distribution is the `.paf.exe` built by the current Installer.

**Why four version parts?**
Windows version resources and the Platform's comparison are 4-part
numeric. `PackageVersion` follows that; the human version lives in
`DisplayVersion`.

**My app is already portable (settings next to the exe). Do I still need
a launcher?**
Yes — a thin one. Point the app at `Data` (its own portable switch, an
environment variable, or `[FilesMove]` for its settings file), and you
still need the generated launcher as `[Control] Start`, for splash,
single-instance handling, and Platform integration.

**The app is .NET/Java. Anything special?**
Declare it: `UsesDotNetVersion` in `appinfo.ini` for .NET; for Java use
`[Activate] Java=find|require` in the launcher INI so Java Portable or a
local JRE is located and `%JAVA_HOME%` set.

**Can a portable app require admin rights?**
Yes, but declare it in both places that apply: `RequiresAdmin=yes` in
`appinfo.ini` and `[Launch] RunAsAdmin` in the launcher INI. Prefer
`try` over `force` when only some features need elevation.

**Can I package this freeware app I like?**
Only if you are its publisher or have the publisher's express consent
(see `docs/09-licensing-permissions-submission.md`). Otherwise, build the
package for your own use and do not distribute it — or ask the publisher.

**Where do I get help?**
The Portable App Development forum at portableapps.com, and the Launcher
manual. Search existing Development Test threads for your app first —
someone may already maintain a package of it.

# 14 — The Beginner Packaging Guide (Distilled, with Modern Corrections)

The original PortableApps.com "Beginner's Development and Packaging Guide"
(a self-described *unfinished* guide, preserved in the Wayback Machine) laid
out the seven steps every packager still follows. They are reproduced here
in substance, each followed by how the step works with today's tools
(Format 3.9, PAL 2.2, Installer 3.9).

## Step 1 — The Idea

Pick an app that would be handy to carry portably. Good candidates do
**not** require Windows administrative rights, do not depend on Windows
services, and do not require internet access (antivirus and system tools
are typically poor candidates). **First check whether a portable version
already exists** — if it does, you're done.

*Today:* also check [`AppConfigs`](13-ecosystem-and-source-repositories.md)
— if PortableApps.com publishes it, its full configuration is there to
learn from.

## Step 2 — The Licensing

Every program is licensed somehow — commercial, shareware, freeware, or
open source. Before packaging, determine whether the licence allows you to
**redistribute** it, **modify** it, or **create a launcher** for it. If it
doesn't, contact the author/publisher and get permission first. Check the
PortableApps.com forums too: the developer may already have stated whether
a portable version is allowed.

*Today:* this is a hard gate, detailed in
[`09-licensing-permissions-submission.md`](09-licensing-permissions-submission.md).
Freeware needs the publisher's express consent and its unmodified official
installer.

## Step 3 — The Analysis

Determine what must change to make the program portable:

- Where does it store settings — registry, INI file, XML, plain text?
- What files does it write, and where? Does it create directories or write
  anywhere else on the local drive?
- Can where it stores settings be changed (command line, environment
  variable, config file)?

Some apps are portable out of the box "if you know where to look." For the
rest, use a monitoring tool — the guide names **RegShot**, **Process
Monitor**, and **RegFromApp**: snapshot the system, run the app, snapshot
again, and compare. The differences are exactly what your launcher must
redirect.

*Today:* do this in a clean VM or Windows Sandbox and record the results
as a trace table mapping every touch point to a launcher mechanism —
[`07-end-to-end-workflow.md`](07-end-to-end-workflow.md), phases 2 and 5.

## Step 4 — The Code

Create a launcher/wrapper that makes the necessary changes when the app
runs and **restores them when it closes**. The guide's era wrote raw NSIS
by hand and recommended studying the Sumatra Portable launcher as the
simplest example.

*Today:* you almost never write the launcher by hand. You write a
launcher INI ([`04-launcher-ini-reference.md`](04-launcher-ini-reference.md))
and the **PortableApps.com Launcher Generator** produces the NSIS launcher.
Hand-written NSIS survives only as `Custom.nsh` hooks for the cases the
INI cannot express ([`05-launcher-advanced-custom-code.md`](05-launcher-advanced-custom-code.md)).

## Step 5 — Compression

Smaller packages take less room on the device and launch faster. The guide
recommended compressing EXEs/DLLs with UPX and recompressing JARs (just
ZIP files with another name) at maximum level with 7-Zip.

*Today:* ⚠️ **Do not follow this step for official-style releases.**
AppCompactor/UPX is **no longer used** for official PortableApps.com
releases — it caused false-positive antivirus detections and breakage.
The `.paf.exe`'s own NSIS compression is sufficient. Skip compression of
the base app's binaries entirely.

## Step 6 — Hosting

The guide pointed open-source packagers at SourceForge free hosting.

*Today:* host source and releases wherever the project lives (GitHub is
typical for community packages). Official distribution is through the
PortableApps.com Platform's app directory after the review process in
[`09-licensing-permissions-submission.md`](09-licensing-permissions-submission.md).

## Step 7 — Testing

Post in the Beta Testing forum so others can test the app and give
feedback to work out bugs.

*Today:* test against the matrix in
[`08-testing-debugging-troubleshooting.md`](08-testing-debugging-troubleshooting.md)
first (first run, persistence, drive-letter change, exit cleanliness,
local-copy coexistence), then post a **Development Test** release in the
forums per [`09-licensing-permissions-submission.md`](09-licensing-permissions-submission.md).

---

(capture of 2019-03-01). The guide's seven-step shape remains the standard
workflow; the annotations above bring each step up to Format 3.9 practice.*

# 15 — Who Uses These Packages, Where, and What That Obliges You to Do

The rest of this knowledge base is written from the packager's chair.
This file is the other side: the people who will run your package, the
places they will run it, and the packaging decisions those facts force.
Items marked *(analysis)* are reasoning about the environment, not
PortableApps.com Format rules. Behaviour marked **Unverified** is not
documented by PortableApps.com — test it yourself before relying on it.

## The jobs you are actually serving

People run portable apps to: use their own apps, settings, and data on a
machine they cannot or may not install software on; try software without
installing it (deleting the folder removes it completely); run an older
version beside a current local install; carry a known-good toolkit
between machines (the IT tech's repair stick); run an app in a language
the host PC is not set to; and keep their data on media they control.
If your package only works on the machine you built it on, it serves
none of these.

People *package* apps to: make a favourite app usable where they can't
install software; ship an official portable edition as the app's
publisher; distribute freeware legally without redistributing it (the
online installer, [`02-installer-and-installer-ini.md`](02-installer-and-installer-ini.md));
portable-ize an existing local install (`[CopyLocalFiles]`); keep an old
app version alive after the new one drops their OS or bitness
(`[LegacyVersions]`); add plugins or locales to an existing package
(plugin installers); or learn how the format works by packaging
something real.

## Who is on the other end — and what breaks for them

| User / situation | What they need | What breaks if you ignore them |
|---|---|---|
| USB roamer (own stick, foreign PCs) | Drive-letter independence, no admin, no traces | The core promise — covered by the migration triple ([`04`](04-launcher-ini-reference.md)) and the leak test ([`08`](08-testing-debugging-troubleshooting.md)) |
| Cloud-drive user (OneDrive/Dropbox/Google Drive, 2+ PCs) | Package survives sync clients | See the cloud row in the environments table — the biggest untested environment |
| Local-disk portable user (folder on C:, prefers no-install) | Same package from a fixed path | Works by design; still test it — "path never changes but the user profile does" is a different case from the stick |
| Shared / family PC user | Their `Data` must not bleed into another Windows user's session; backup/restore must be per-user safe | One user's run restores *another* user's local settings. Test with two accounts ([`08`](08-testing-debugging-troubleshooting.md)) |
| School / library / kiosk user | Runs as guest/standard user; profile may be wiped at logoff | Data "vanishes" — because it was never on the stick. help.html must say data lives in the package folder, not on the PC |
| Locked-down corporate user | No HKLM writes, no elevation available | See the policy row below |
| User with poor / no connectivity | Full installers that work air-gapped; online installers that fail clearly | A half-installed package and no explanation |
| Privacy-conscious user | Zero host leftovers — and honesty about OS-level traces no launcher can remove ([`18-security-privacy-and-abuse.md`](18-security-privacy-and-abuse.md)) | Over-trusting "no trace" |
| User who also has the app locally | Both copies' settings untouched | Covered thoroughly in [`03`](03-launcher-overview.md)/[`08`](08-testing-debugging-troubleshooting.md) |
| User on old hardware / old Windows | Honest `MinOS`; a legacy spin-off when support is dropped | Covered: [`04`](04-launcher-ini-reference.md) `MinOS`/`MaxOS`, [`02`](02-installer-and-installer-ini.md) `[LegacyVersions]` |
| User with a huge profile (browser/mail archives) | Startup not dominated by moving gigabytes | Prefer in-place redirection over moves ([`08`](08-testing-debugging-troubleshooting.md), Performance sanity) |
| User who loses the stick | Knowing the folder copy *is* the backup, and `Data` is the irreplaceable part | The template help.html now says this explicitly |

## Environments beyond the happy path

| Environment | What to do |
|---|---|
| Cloud-synced folder (OneDrive, Dropbox, Google Drive) | *(analysis)* Sync clients lock files and may deliver placeholder (not-yet-downloaded) files, and two PCs can sync `Data` between runs, producing conflict copies of settings and `.reg` files. Prefer in-place redirection (environment variables, the app's own portable mode) over `[FilesMove]`/`[DirectoriesMove]` copy-back, which multiplies lock conflicts. Never claim cloud-folder support you have not tested with the sync client running, on two machines. PAL behaviour under sync clients is **Unverified**. |
| Policy-managed PC (school, library, employer) | *(analysis)* Group Policy / AppLocker can block executables from removable media and writes to HKLM; no package setting overrides policy. Design HKCU-only where the app allows it, use `RunAsAdmin=try` rather than `force` so a refusal degrades instead of dead-ending, and do not promise these machines in help.html. |
| Windows Server / multi-session hosts, Fast User Switching | **Unverified** — PAL behaviour when two users run the same portable copy concurrently is not documented. Do not claim it. |
| Slow removable media (USB 2, cheap flash) | Minimise move-in/move-out volume. A browser-sized profile shuttled over USB 2 is a failed package even if it is a correct one. |
| Nearly-full drives | The installer checks free space using `AdditionalInstallSize` — keep it honest ([`02`](02-installer-and-installer-ini.md)). *(analysis)* Also consider the host drive: Live mode and the contained temp dir need room on the host, not just the stick. |
| Long and deep paths | *(analysis)* Path-length limits bite in three places: where the user puts the package, how deep `Data` grows, and the Live-mode temp copy. Keep package-internal paths short, avoid deep `DefaultData` trees, and test from a deliberately deep folder (200+ characters). |
| Filesystem of the medium | *(analysis)* FAT32 cannot hold a single file over 4 GB and has no ACLs; exFAT/NTFS differ again. If the base app creates large single files, say so in help.html rather than letting it fail on a FAT32 stick. |
| Non-English Windows | Test on a non-English Windows image if you claim multilingual support: installer `[Languages]`, the `[Language]`/`[LanguageFile]` chain, and `FileWrite` `Encoding` are separate systems and each can fail alone. *(analysis)* Apps that store settings in the system ANSI code page can corrupt non-ASCII data when the package moves between differently-localed PCs — if your trace shows ANSI settings files, note it in help.html. |
| Stored window positions | *(analysis)* Settings files often store window geometry. A position saved on a dual-monitor or high-DPI machine can open off-screen on the next PC. This is a portability trace like any other: if the app stores geometry, test first run on a single small display. |
| Offline machines | An online installer is a promise of network. If the app must work air-gapped, ship a full (non-online) installer and say the online one needs internet in its description. A failed download must never be "fixed" by removing `DownloadSHA256` ([`02`](02-installer-and-installer-ini.md)). |
| Antivirus-heavy environments | On-access scanning can slow first runs, lock files during move-back, or quarantine a generated launcher. See [`18-security-privacy-and-abuse.md`](18-security-privacy-and-abuse.md) — and never "fix" false positives with UPX/AppCompactor ([`14`](14-beginner-packaging-guide.md)). |
| Wine as a *run* target | Only the uroesch build route is documented ([`13`](13-ecosystem-and-source-repositories.md)). PAL-on-Wine runtime support is **Unverified**; an optional Wine run is in the [`08`](08-testing-debugging-troubleshooting.md) matrix. |
| ReactOS | Never claimed by any source this repo is built on. **Unverified** — do not claim it. |
| 32-bit app on 64-bit Windows (WoW64) | *(analysis)* A 32-bit base app's registry/file writes may be redirected by WoW64 on 64-bit Windows, so a RegShot trace taken on one bitness can mislead on the other. Trace on the bitness you ship for, or on both. |

## Inputs are wider than the base app

Every input a package consumes is a place it can break — or be broken:

- **Base app in every shape**: Inno installer, ZIP/7z archive, MSI,
  NSIS/other EXE installer, plain folder, existing local install
  (`[CopyLocalFiles]`), single EXE/JAR/.NET assembly. Extraction
  mechanics are in [`02`](02-installer-and-installer-ini.md); the worked
  examples cover Inno and ZIP. MSI is listed among the formats the
  Installer's online mode can extract, but this repo has no worked MSI
  example — verify your exact input format with a test build
  (**Unverified** beyond the Inno/ZIP cases).
- **The online download**: direct URL, redirect chain, knock page
  (`DownloadKnockURL`), publisher re-issue under the same URL, an
  interrupted download. There is **no mirror/fallback key** —
  `Download2*` is a *second file*, not an alternative source for the
  first. If `DownloadURL` dies, the install fails; the fix is a new
  package release, never a removed hash.
- **The user's own documents**, opened via the app (Open With,
  drag-and-drop, Platform associations, Send To). These are untrusted
  input forwarded *through the launcher* — quoting bugs become
  argument-injection bugs ([`18`](18-security-privacy-and-abuse.md)).
- **Command-line arguments to the launcher exe**, forwarded to the app
  in addition to `CommandLineArguments` — including the quote-stripping
  surprise in [`04`](04-launcher-ini-reference.md).
- **The user config INI** next to the exe — runtime-read, user-writable,
  therefore untrusted ([`18`](18-security-privacy-and-abuse.md)).
- **Host state**: environment variables (a broken/hostile `PATH`
  affects DLL loading), a local install's registry state, and `Data`
  written by an *older package version* — the input nobody re-tests.
  Settings migrations across versions are a maintainer task:
  [`16-updating-a-package.md`](16-updating-a-package.md).
- **Language signals that can disagree**: Platform variables, Windows
  locale, installer UI language, the app's own language files. The
  chain and its fallback order are in
  [`04`](04-launcher-ini-reference.md)/[`06`](06-environment-variables.md)/[`10`](10-platform-integration.md);
  wire it end-to-end or the app silently runs in its default language.

# 16 — Updating an Existing Package (the Maintainer's Workflow)

Most packaging work is not new packages; it is new versions of the base
app in an existing package. The greenfield workflow
([`07-end-to-end-workflow.md`](07-end-to-end-workflow.md)) still applies,
with these deltas:

1. **Re-run the trace analysis on the NEW base-app build** in a clean VM
   ([`07`](07-end-to-end-workflow.md) Phase 1). New versions add settings
   locations and retire old ones; last version's trace inventory is a
   hypothesis, not a fact. Pay attention to bitness: a trace taken on
   64-bit Windows can mislead for a 32-bit build under WoW64
   ([`15`](15-users-contexts-and-environments.md)).
2. **Decide what happens to existing users' `Data`.** The installer's
   preservation rules ([`02-installer-and-installer-ini.md`](02-installer-and-installer-ini.md))
   decide which folders survive an upgrade. If the base app changed its
   settings format or location, an upgrade can strand the old settings
   in place, unread. The production pattern for a real migration is
   installer custom code that copies the old layout forward on upgrade,
   backing up first — see the Notepad++ set in
   [`../examples/real-world/`](../examples/real-world/) (its
   `PortableApps.comInstallerCustom.nsh` moves a legacy `Data\settings`
   layout to `Data\Config` in `CustomCodePreInstall` and finishes in
   `CustomCodePostInstall`).
3. **`DefaultData` only populates an EMPTY `Data` folder.** Changing
   `DefaultData` in a new release does nothing for existing users. If a
   new default must reach them, that is a `[FileWriteN]` or custom-code
   job, not a `DefaultData` edit — a mistake maintainers make routinely.
4. **Re-verify the payload deliberately.** For online installers,
   re-download the `[DownloadFiles]` target and re-pin `DownloadSHA256`
   ([`02`](02-installer-and-installer-ini.md)). For bundled packages,
   verify the new base-app download against the publisher's signature or
   published hash before bundling it
   ([`18-security-privacy-and-abuse.md`](18-security-privacy-and-abuse.md)).
   A hash change you did not make is a stop sign, not a nuisance.
5. **Bump versions per [`01`](01-format-spec.md)**: new app version in
   the first `PackageVersion` parts, packaging revision in the last;
   `DisplayVersion` states the new base-app version honestly.
6. **Run the upgrade test, checking specifics**
   ([`08`](08-testing-debugging-troubleshooting.md) +
   pre-release checklist): install the *previous* package, create real
   settings, install the new `.paf.exe` over it — then verify the
   specific preserve/remove entries did what they say, the migrated
   settings open in the new version, and files scheduled for removal are
   actually gone. "Settings survived" in general is not the test.
7. **Check the legacy cutoffs.** If this release drops 32-bit Windows or
   an old Windows version, the `[LegacyVersions]` cutoff versions must
   name *this* release, and the legacy launcher files must be present in
   `Other\Source\Legacy\<SuffixFolder>`
   ([`02`](02-installer-and-installer-ini.md),
   [`17-failure-mode-reference.md`](17-failure-mode-reference.md)).
8. **Audit `Data\settings` drift.** If you removed a `[RegistryKeys]`
   entry, existing users still carry its old `.reg` file. Note stale
   files in the release notes; an obsolete key can be re-imported if the
   entry ever returns.

# 17 — Failure-Mode Reference

Symptom-driven companion to
[`08-testing-debugging-troubleshooting.md`](08-testing-debugging-troubleshooting.md).
That file covers the common problems; this one is the exhaustive list,
organised by lifecycle stage. Every fix below uses only mechanisms
documented in [`01`](01-format-spec.md)–[`06`](06-environment-variables.md).
Where neither this repo nor the manual it mirrors documents the tool's
behaviour, the entry says **Unverified** — do not guess past it.

## A. Authoring and generation

| Failure | Cause | Symptom | Prevention / Fix |
|---|---|---|---|
| A key is misspelled or invented | **PAL has no documented error for unknown INI keys — treat them as silently ignored.** The compile-failure safety net in [`05`](05-launcher-advanced-custom-code.md) applies to `${Segment…}` macros in custom code, **not** to INI keys | A move, cleanup, or wait silently never happens; settings leak or reset with no error anywhere | Diff every key against [`04`](04-launcher-ini-reference.md) before generating (package checklist). Confirm behaviour with a debug build ([`08`](08-testing-debugging-troubleshooting.md)), never by assumption |
| Duplicate section or key in one INI | Merged edits | **Unverified** — which value wins is not documented | Keep exactly one instance of each section/key; reconcile merges by hand |
| INI file saved in the wrong encoding | Editor/AI writes UTF-8-BOM or UTF-16 | **Unverified** — the required encoding of `appinfo.ini` / `installer.ini` / the launcher INI is not stated in this repo | Save the three INIs in the same encoding as the shipped Application Template files; if values parse strangely, re-save from the template and re-add values |
| Numbered sections have a gap (`[FileWrite1]`, `[FileWrite3]`) | Renumbering slip | Entries after the gap may never be processed (**Unverified**) | Number consecutively from 1 in `[FileWriteN]`, `[ServiceN]`, and every integer-keyed cleanup/preserve/remove list (package checklist) |
| `.reg` path replace never matches | The `.reg` is UTF-16LE without a BOM, so `Encoding=auto` cannot detect it | Drive-letter migration silently does nothing for registry-stored paths | Set `Encoding=UTF-16LE` on the `Replace` sections targeting that `.reg` ([`04`](04-launcher-ini-reference.md)) |
| `Debug.nsh` shipped in a release | Debug file left in `App\AppInfo\Launcher\` at build time | Users get message-box pauses and a `Data\debug.log` | Delete `Debug.nsh` and regenerate before building the release installer; the pre-release checklist verifies its absence |
| Generator cannot find NSIS | NSIS Portable (Unicode) is not installed as the sibling folder `NSISPortable` next to the Launcher ([`03`](03-launcher-overview.md)) | Generation fails with a makensis error | Install per [`03`](03-launcher-overview.md). The ANSI variant is not used |
| Harmless include warnings treated as blockers (or real errors waved through) | Missing `Custom.nsh`/`Debug.nsh` produce `!include: could not find` **warnings** ([`08`](08-testing-debugging-troubleshooting.md)) | Either needless empty files are created, or a real NSIS error is ignored | Warnings about the two optional includes are expected when the files are absent. Any other NSIS error is a failure: fix the first error line ([`05`](05-launcher-advanced-custom-code.md)) |
| Legacy `Custom.nsh` silently moves at first compile | The Generator upgrades the pre-2.1 `Other\Source` location automatically ([`05`](05-launcher-advanced-custom-code.md)) | File appears/disappears in source control unexpectedly | Commit the move; the current location is `App\AppInfo\Launcher\Custom.nsh` |
| Installer wizard rejects the package | `appinfo.ini`/`installer.ini` validation | Wizard stops with an error | The wizard validates, but this repo does not enumerate its checks (**Unverified** in detail) — correct the metadata against [`01`](01-format-spec.md)/[`02`](02-installer-and-installer-ini.md) and rebuild |

## B. Installer build

| Failure | Cause | Symptom | Prevention / Fix |
|---|---|---|---|
| EULA displays garbled | `EULA.txt` saved ANSI | Mojibake in the install wizard | Save `EULA.txt` as Unicode ([`02`](02-installer-and-installer-ini.md)) |
| Changed EULA never re-shown | `EULAVersion` in `[License]` not bumped when the text changed | Returning users install under a EULA they never saw | Bump `EULAVersion` with every EULA text change ([`02`](02-installer-and-installer-ini.md)) |
| Installer UI misses languages | `[Languages]` present without `ENGLISH=true` (required), or languages not enabled | English UI unavailable / wizard in the wrong language | `ENGLISH=true` is required whenever the section exists; every other language defaults to `false` — enable the ones the package supports ([`02`](02-installer-and-installer-ini.md)) |
| Optional section installs nothing | `[OptionalComponents]` enabled but no `OptionalDirectory#`/`OptionalFile#` listed | Optional content silently absent | List the optional content explicitly ([`02`](02-installer-and-installer-ini.md)) |
| Free-space check underestimates | `AdditionalInstallSize` absent or too small | Install starts, then fails partway on a nearly full drive instead of refusing cleanly | Set `AdditionalInstallSize` to the real extracted size in KB ([`02`](02-installer-and-installer-ini.md), example 06); test the near-full-drive case ([`08`](08-testing-debugging-troubleshooting.md)) |
| Legacy copy is broken | `[LegacyVersions]` configured but the replacement launcher files are missing from `Other\Source\Legacy\<SuffixFolder>` | The spun-off legacy package has no working launcher | Ship the legacy launcher EXE(s), INI, and `custom.nsh` in that folder ([`02`](02-installer-and-installer-ini.md)); test an upgrade on the legacy OS / 32-bit Windows |
| 11th preserve/remove entry | Lists are capped at 10 entries each ([`02`](02-installer-and-installer-ini.md)) | Entries past the cap are not honoured (**Unverified**) | Consolidate paths — preserve a parent directory instead of many children |

## C. Install time

| Failure | Cause | Symptom | Prevention / Fix |
|---|---|---|---|
| Online install on an offline machine | No network at install time | Download cannot start. The installer's exact error/retry behaviour is **Unverified** | Nothing in the package can fix this; the `_online.paf.exe` name is the user-facing warning. Test once offline so the failure is at least understood |
| Download URL returns 404 or an HTML page | Publisher moved/restructured the file | Hash check fails (for an HTML page) or the download fails outright | Update `DownloadURL`, `DownloadSHA256`, and the extraction keys together, after downloading and verifying the new file yourself ([`02`](02-installer-and-installer-ini.md)). Never delete the hash to "fix" it |
| Knock URL no longer works | The page behind `DownloadKnockURL` changed (cookie/token flow) | Main download is refused or returns a login page, which then fails the hash check | Re-check the knock flow against the publisher's current site; update `DownloadKnockURL` and re-verify the hash ([`02`](02-installer-and-installer-ini.md)) |
| Redirect loop at the publisher | Publisher-side redirect chain | Download never completes (**Unverified** installer behaviour) | Point `DownloadURL` at the final file URL, not a redirecting landing URL; verify by downloading the URL yourself before recording the hash |
| Extraction produces an empty/partial app folder | `AdvancedExtract…Filter` matches nothing (`*` used where `**` was needed, or a wrapper folder not accounted for), or a nested archive was not declared with `DoubleExtract…` | Install "succeeds"; first run fails with the ProgramExecutable-not-found error ([`08`](08-testing-debugging-troubleshooting.md)) | After building, install fresh and inspect the extracted `App\<AppName>` tree file-by-file against the publisher's archive (use 7-Zip to inspect the source archive, [`11`](11-tools-and-versions.md)). Narrow/widen filters per example 06 |
| Antivirus quarantines a file mid-install | AV false positive, or a genuinely replaced publisher file | Partial `App` tree; app fails to start or behaves strangely | Reinstall to a clean folder after the AV decision is resolved; verify the publisher file's hash out-of-band before trusting it. Do not UPX/AppCompactor the binaries — a documented cause of false positives ([`14`](14-beginner-packaging-guide.md)) |
| Target path is very long | PortableApps folder nested deeply, or a long user-chosen parent path | Behaviour **Unverified** — neither installer nor launcher path-length limits are documented in this repo | Install and test from the deepest path you intend to support ([`15`](15-users-contexts-and-environments.md)); prefer short parent paths in your documentation |
| Target folder is being cloud-synced | Sync client locks files during install/upgrade and creates conflict copies of `Data` files | Locked-file install errors; duplicated settings files; settings "reverting" | Not addressed by the format. Advise users to install outside synced folders; if files are locked, pause syncing and reinstall ([`15`](15-users-contexts-and-environments.md)) |
| Downgrade: older `.paf.exe` run over a newer install | User runs an old installer | **Unverified** — the Installer is not documented to block downgrades ([`10`](10-platform-integration.md) covers update *offers* only) | Packager-side discipline only: keep `PackageVersion` monotonic ([`09`](09-licensing-permissions-submission.md)) and label old downloads clearly. Do not rely on the installer to refuse |
| Upgrade leaves locked files behind | App process closed, but a child process or shell extension still holds a file | Some binaries are not replaced; mixed-version install | Close the whole process tree before upgrading; if replacement failed, reinstall to a fresh folder and copy `Data` over. Keep `[CheckRunning]` working — `CloseEXE` must name the real exe ([`02`](02-installer-and-installer-ini.md)) |
| Read-only install target | User picks a location they cannot write to | Install fails (**Unverified** installer behaviour) | Install somewhere writable. Note this is different from *running* from read-only media, which is Live mode ([`03`](03-launcher-overview.md)) |

## D. Runtime

| Failure | Cause | Symptom | Prevention / Fix |
|---|---|---|---|
| Paths stored with forward slashes (or in `java.util.prefs` form) never migrate | The migration triple ([`04`](04-launcher-ini-reference.md)) only covers backslash forms | App loses its data store after a move, despite a correct-looking triple | Add `Replace` sections using the `:ForwardSlash` / `:java.util.prefs` forms of the same variables (documented in [`06`](06-environment-variables.md)), in the same most-specific-first order |
| Settings under HKLM or `C:\ProgramData` fail for standard users | Those locations need admin rights; the app writes nothing (or fails) unelevated | Settings reset every run for non-admin users only | Cover the location with `[RegistryKeys]`/`[DirectoriesMove]` like any other (roots include HKLM, [`04`](04-launcher-ini-reference.md)), or declare the requirement (`RequiresAdmin` in appinfo.ini + `[Launch] RunAsAdmin`). Test as a limited user ([`08`](08-testing-debugging-troubleshooting.md)) |
| App stores data in the host Documents folder | A trace class with no worked example | User documents/profiles land on the host and stay there | Treat it like any other folder trace: `[DirectoriesMove]` with the host path built from `%DOCUMENTS%` (host) — not `%PortableApps.comDocuments%` ([`06`](06-environment-variables.md)) |
| Two portable instances corrupt shared settings | `SinglePortableAppInstance` defaults to `false` | Interleaved writes to the moved settings/`Data` | Set `SinglePortableAppInstance=true` for apps whose settings cannot survive concurrent access ([`04`](04-launcher-ini-reference.md)) |
| Host `%TEMP%` fills with app leftovers | `[Launch] CleanTemp=false` | Leak test finds app temp files on the host | Leave `CleanTemp` at its default `true` unless the app provably leaves nothing in TEMP ([`04`](04-launcher-ini-reference.md)) |
| .NET app launched directly (not via the Platform) on a machine without .NET | The `UsesDotNetVersion` warning/blocking is a **Platform** behaviour ([`10`](10-platform-integration.md)); the launcher itself has no documented .NET check | Obscure OS/framework error instead of a clear message | Declare `UsesDotNetVersion` in appinfo.ini regardless; if a clear message matters for direct launches, that requires custom code ([`05`](05-launcher-advanced-custom-code.md)) — there is no INI key for it |
| 64-bit-only app on 32-bit Windows, undeclared | `Requires64bitOS` omitted | Obscure OS loader error; Platform does not hide/block the app | Set `Requires64bitOS=yes` in `[Dependencies]` ([`01`](01-format-spec.md)/[`10`](10-platform-integration.md)) |
| `[LanguageStrings]` key form mismatch | Key written `pt_BR` where the base value is `pt-br` | Lookup misses; `%PAL:LanguageCustom%` falls back to the base value and the app runs in the wrong language | Copy key forms exactly from the language-variable values in [`06`](06-environment-variables.md); use `[Language] Default` deliberately |
| Live-mode temp copy fails or misbehaves | Host `%TEMP%` tiny/full, or `[LiveMode] CopyApp=false` changes `%PAL:AppDir%` semantics under the INI's assumptions | App fails to start from read-only media | Test Live mode explicitly ([`08`](08-testing-debugging-troubleshooting.md)); remember `Data` is always copied in Live mode — `CopyData` is obsolete ([`04`](04-launcher-ini-reference.md)) |

Never rely on `DefaultData` as an upgrade mechanism ([`16`](16-updating-a-package.md)) |

# 18 — Security, Privacy, and Abuse

The rest of this knowledge base is about correctness. This file is the
threat side: who can attack a package, a packager, or a user, and what
the format does — and does not — do about it. Items marked *(analysis)*
are security reasoning applied to documented behaviour; items marked
**Unverified** are not established by the sources this repo is built on.

## Threat model in one page

**Assets at risk**

- **The host PC's integrity.** The launcher deliberately writes to the
  host registry, `%APPDATA%`, and TEMP, then restores them
  ([`03`](03-launcher-overview.md)). Anything that breaks the
  backup/restore symmetry — or a package that never intended to
  restore — leaves persistent changes. With `RunAsAdmin`, the package
  runs elevated.
- **The user's portable data.** All settings, profiles, and saved
  credentials live in `Data\`, in the clear, on removable media.
- **The publisher's reputation.** A trojanized repack is distributed
  under the publisher's name and icon.
- **The format's trust.** Users are trained that `.paf.exe` means safe
  and vetted. That trust attaches to the *format*, so any `.paf.exe`
  from any site borrows it.
- **The packager's build machine.** Packaging executes untrusted code by
  design: the base app runs during analysis, custom code is compiled
  into the launcher and runs at install/launch time.
- **The host user's data (reverse direction).** The launcher reads and
  copies a local install's settings to back them up, and
  `[CopyLocalFiles]` imports local files into the package. A hostile
  package can walk away with host data inside its `Data\`.

**Attackers**: a malicious packager; a compromised upstream publisher;
a network attacker on the install-time download path; a malicious
document opened in the app; a hostile host machine the stick is plugged
into; a co-user with write access to the package folder; and fake
"portable apps" download sites.

## Security rules for packagers

1. **Licensing is a security control, not paperwork.** The
   publisher/consent rule ([`09`](09-licensing-permissions-submission.md))
   is what separates an official package from a trojanized one. Never
   package what you cannot account for.
2. **Verify the base app before you bundle it.** Download only from the
   publisher's canonical URL; check the publisher's signature or hash
   where offered; record the source URL and the SHA-256 of what you
   bundled. A compromised upstream download becomes a compromised
   package that passes every format check.
3. **Online installers: HTTPS + pinned hash, always.** `DownloadURL`
   (and `DownloadKnockURL`, if unavoidable) must be the publisher's own
   HTTPS address, and `DownloadSHA256` must always be set. A hash proves
   the payload is the file the *packager chose* — it does not prove the
   file is safe or that the publisher made it. Never delete or blank a
   hash to fix a failed install; re-verify the new file and update the
   hash deliberately ([`02`](02-installer-and-installer-ini.md)).
   Whether the downloader enforces HTTPS is **Unverified** — require it
   by policy.
4. **Custom code is code.** `Custom.nsh`,
   `PortableApps.comInstallerCustom.nsh`, and `Debug.nsh` are arbitrary
   NSIS that run at launch/install time — possibly elevated. Read every
   line of any file you copy from AppConfigs, a forum, or a template
   repo before generating. Prefer INI over custom code; justify any
   `${DisableSegment}` / `${OverrideExecute}` in writing.
5. **Least elevation.** Default `RunAsAdmin=none`. Use `try` before
   `force`; use `compile-force` only with a written justification (it
   removes the explanatory message and gets a conditioned UAC click).
   Declare `RequiresAdmin=yes` in appinfo.ini whenever elevation is
   used, so the Platform can surface it before install.
6. **A package that installs a service or driver is not a PAL
   package.** Services are disabled in PAL 2.2
   ([`04`](04-launcher-ini-reference.md)). Do not route around that with
   custom code; treat any third-party package that does as untrusted
   until manually reviewed. This disablement is a load-bearing safety
   property of the format.
7. **Scope destructive sections like a loaded tool.**
   `[RegistryCleanupForce]` and `[DirectoriesCleanupForce]` delete
   unconditionally on every exit. List only trees your trace inventory
   proved the app creates; prefer the `IfEmpty` variants; use the `-`
   discard form for keys the app must never persist
   ([`17`](17-failure-mode-reference.md) §E).
8. **Treat `[CopyLocalFiles]` and broad `[RegistryKeys]` lists as
   data-access declarations** — the portable equivalent of app
   permissions. They copy host files/registry data into the package.
   Include them only when the feature needs them, scope them to exact
   paths/keys, and say in help.html what is copied.
9. **No code through `Data`.** Binaries belong in `App\` (Format rule).
   Never use `[FilesMove]`/`[DirectoriesMove]` to shuttle DLLs or
   scripts through `Data\`. Declare real plugin folders with
   `[SpecialPaths] Plugins` and tell users that folder is code.
10. **Keep `CleanTemp=true`** and `SupportsUNC` at `warn`/`no` unless
    UNC operation is a tested requirement. Do not add `PATH` entries or
    `WorkingDirectory` overrides pointing outside the package.
11. **Mind what `Data` contains.** Settings and `Data\settings\*.reg`
    files are plaintext and may hold credentials (see Privacy below).
12. **Truthful metadata is a security property.** `[License]` booleans,
    `DisplayVersion`, `Homepage`, and `Donate` are rendered in the
    Platform and drive update decisions ([`10`](10-platform-integration.md)).
    A `PackageVersion` bump that does not match the stated release is a
    release-blocking defect — version comparison is not authenticity.
13. **Get the tools only from portableapps.com** and record their
    versions ([`11`](11-tools-and-versions.md)). A patched or
    third-party Generator/Installer changes the trust base of
    everything it builds; label such builds unofficial.
14. **Do not ship debug builds.** Remove `Debug.nsh` before release
    ([`08`](08-testing-debugging-troubleshooting.md)): a shipped
    `Data\debug.log` leaks full paths and segment traces to anyone who
    later holds the stick.

## The risks behind the rules (summary)

| Risk | Mechanism in one line | Covered by |
|---|---|---|
| Trojanized repackaging | Anyone can build a `.paf.exe`; provenance and review are the only separators | Rule 1; [`09`](09-licensing-permissions-submission.md) |
| Compromised upstream (bundled) | Packager bundles a poisoned download once; no downstream check exists | Rule 2 |
| Online-installer substitution | MITM/mirror serves a bad file; hash stops it only if the installer itself is genuine | Rule 3 |
| DLL search-order hijacking *(analysis)* | Windows loads DLLs from the app's own folder first; that folder is on writable removable media | Rule 9/10; treat the package folder as trusted-code territory |
| No runtime integrity check *(analysis)* | The launcher INI is compiled in, but nothing verifies the *files*: replace `App\…\App.exe` or a DLL beside it and the genuine launcher runs the replacement | Tell users (help.html note below) to re-install from the original `.paf.exe` if a folder's provenance is doubtful |
| User config INI injection *(analysis)* | `<AppID>.ini` next to the exe is runtime-read and writable: `AdditionalParameters` and custom `${ReadUserConfig}` keys can change what runs | Rule 4 applies to custom keys too: validate values in `Custom.nsh`, document them in help.html |
| Argument injection via opened files *(analysis)* | Crafted filenames/URLs pass through `[Associations]` patterns and PAL's weak quote-stripping into the app's command line | Quote `%1` in patterns; run the hostile-filename test in the pre-release checklist |
| UNC attacks *(analysis)* | Running from `\\server\share` loads binaries over the network from that server and can expose the user's NTLM credential material to it | Rule 10 |
| Temp races / Live-mode exposure *(analysis)* | Temp names are fixed (`…PortableTemp`, `…PortableLive`); Live mode copies all of `Data` onto the host disk for the run. Whether PAL fails safe if the temp path already exists with hostile contents is **Unverified** | Rule 10; warn users in help.html |
| Update channel abuse *(analysis)* | Updates compare `PackageVersion` only; `DisplayVersion` never gates anything; `Homepage`/`Donate` are packager-controlled links in a trusted UI | Rule 12 |
| Extraction reaching outside the target *(partly Unverified)* | `[CopyLocalFiles]`, `<ROOT>` extract targets, `[LegacyVersions]`, and plugin installers deliberately write outside `<parent>\<AppID>`; 7-Zip path-traversal protection on hostile archives is **Unverified** | Review any installer.ini using them as privileged configuration |
| Java resolution *(Unverified)* | PAL's search order for `[Activate] Java=find` is not documented in this repo; prefer `require` + Java Portable for sensitive apps | Rule 13's spirit: know your toolchain |

## Privacy

- **Leave-no-trace is the format's core privacy control**, and it is
  only as good as the trace inventory
  ([`01`](01-format-spec.md) §4, [`08`](08-testing-debugging-troubleshooting.md)
  leak test). Done wrong, the traces are: registry keys and `%APPDATA%`
  leftovers (covered), Qt per-path cache keys (`[QtKeysCleanup]`), and
  crash dumps written by the app or Windows Error Reporting to host
  locations outside every move/cleanup section *(analysis)*.
- **What portability cannot hide** *(analysis)*: OS-level traces no
  launcher can remove — Prefetch records (exe name, path, run times),
  recent-items/jump-list entries for files you opened, thumbnail
  caches, and the host registry's USB device history. Never advertise a
  package as forensic-proof; state the limit instead.
- **`Data` is plaintext.** Settings files and the
  `Data\settings\*.reg` exports may contain credentials, tokens, and
  private keys in clear text. **A lost or stolen stick is a full
  profile compromise** for browsers, mail clients, and FTP/SSH tools.
  If the base app has a master-password or encrypted-vault option,
  enable or recommend it in help.html, and advise users carrying
  sensitive apps to encrypt the drive itself (e.g. BitLocker To Go).
  Never describe a package as "private" without these caveats.
- **Sync is silent replication.** If the PortableApps folder sits inside
  OneDrive/Dropbox/Google Drive, `Data` — including the plaintext
  `.reg` files — is copied to third-party servers and every synced
  machine ([`15`](15-users-contexts-and-environments.md)).
- **Metadata travels with the folder.** Settings files contain absolute
  paths from every machine the package has run on (that is why the
  migration triple exists); `pac_installer_log.ini` records install
  times and versions; `Data\debug.log` can contain full paths. Users
  sharing a `Data` folder for bug reports should inspect it first.
- **The base app's network behaviour is unchanged.** Packaging moves
  where an app stores data, not what it sends. Telemetry and cloud
  features still phone home — now from every host the stick visits.
  Where the app has an offline mode or a telemetry opt-out settable via
  `[RegistryValueWrite]`/`[FileWriteN]`, using it is a privacy
  improvement worth documenting in help.html.

## Abuse cases (know them; don't build for them)

- **Policy bypass.** "No installation, no admin" is indistinguishable
  from a tool for evading workplace/school software policy. That is the
  user's legal/disciplinary risk, and packagers should not market
  packages as policy-evasion tools.
- **Portable malware toolkits.** Password-recovery and network tools are
  legitimate `Security`/`Utilities` apps and standard attacker kit. The
  format is neutral; official-distribution review
  ([`09`](09-licensing-permissions-submission.md)) is the only gate, and
  it binds only official distribution.
- **License circumvention.** Packaging commercial software to defeat
  its installation/activation is forbidden by the Format
  ([`09`](09-licensing-permissions-submission.md)). False `[License]`
  booleans that make redistribution look authorised are the soft form
  of the same abuse.
- **Fake "portable" download sites.** The highest-volume real-world
  abuse: SEO-poisoned sites offering "AppName Portable" downloads that
  are adware/malware wearing the format's name, icon, and
  `.paf.exe` naming convention — a convention anyone can copy. The
  anti-impersonation controls (official distribution, third-party
  `AppID` suffixing) bind only honest packagers.
- **Anti-forensic use.** Leave-no-trace plus Live mode's
  copy-run-delete cycle is a privacy feature and an anti-forensic
  feature. Document its limits (above) rather than letting users
  over-trust it.
- **Online installers as scan evasion.** A small clean downloader whose
  payload arrives at install time defeats static scanning of the
  distributed file. `DownloadSHA256` does not help here — a malicious
  packager pins the hash of a malicious payload. Reviewers of online
  installers must fetch and inspect the *payload*, not just the
  installer.ini.

## Suggested help.html wording (trust and privacy note)

> Download this package only from PortableApps.com or the app
> publisher's own site. Other sites offering "portable" versions of
> well-known apps are a common malware channel, whatever the file is
> named. Third-party (non-PortableApps.com) packages are unsigned;
> Windows may warn the first time you run one — check where the file
> came from instead of dismissing the warning by habit. Your settings
> live in the `Data` folder in plain form, like most apps' settings; if
> you carry accounts or credentials in this app, encrypt the drive (for
> example with BitLocker To Go). The extracted package folder is
> program files: if anyone else could have changed files in it, delete
> it and re-install from the original `.paf.exe`. Running from a
> network share (`\\server\share`) loads the program over the network
> and can expose your Windows credentials to that server — copy the
> package to a drive you control first.

# 19 — Accessibility

Accessibility is a property of the *package*, not just the base app.
PAL and the Installer are fixed tools — their UI is inherited and may
not be modified (AGENTS.md: never modify the Installer's own code) —
but the packager controls the metadata, the language chain, the splash
behaviour, help.html, and the icons, and each of those can include or
exclude users. Items below trace to the format documentation in
[`01`](01-format-spec.md)–[`06`](06-environment-variables.md); where
this repo's sources are silent, the entry says **Unverified** rather
than guessing.

## What you are given (do not break it)

- **The install wizard's language set.** If installer.ini has a
  `[Languages]` section, `ENGLISH=true` is required and every other
  language defaults to `false` ([`02`](02-installer-and-installer-ini.md)).
  A packager who adds the section carelessly ships an English-only
  wizard. Enable the languages the package actually supports.
- **Optional components pre-selected for non-English installs**
  (`OptionalSectionPreSelectedIfNonEnglishInstall`, default `true`) —
  language packs arrive selected for the users who need them. Leave the
  default unless you have a reason.
- **A keyboard-free path exists**: silent / Platform-driven installs
  need no wizard interaction at all.
- **A predictable destination**: the user picks a parent folder and the
  installer appends the app folder. Say so in help.html; predictability
  is a cognitive-accessibility feature.
- **The EULA as plain Unicode text** (`App\AppInfo\EULA.txt`) — readable
  by assistive technology as-is. Keep it that way (Unicode, not ANSI).
- **No launcher interaction is time-limited.** The one timed element is
  the splash screen (`SplashTime`, default 1500 ms), and users can turn
  it off (user config `DisableSplashScreen`, or the Platform option).
  Document that switch in help.html.
- **Warnings before install**: `[Dependencies]` declarations
  (`RequiresAdmin`, `Requires64bitOS`, `UsesDotNetVersion`) surface in
  the Platform *before* a user commits to a package that cannot run for
  them. Declaring them honestly is an accessibility duty, not metadata
  trivia.

## What you must do

- **Write the Description like it is the only description.** For a
  screen-reader user browsing the store, the ≤512-character
  `Description` in appinfo.ini ([`01`](01-format-spec.md)) may be all
  they get. Plain language, what the app does, no marketing filler.
  `Category` must be the exact English string even for non-English
  apps — it is a machine value, not display text.
- **Wire the language chain end-to-end.** Platform locale variables
  ([`06`](06-environment-variables.md)) → `[Language]` /
  `[LanguageStrings]` building `%PAL:LanguageCustom%` → `[LanguageFile]`
  fallback for launches outside the Platform — and then actually *pass*
  the variable to the app. A chain that stops one step early runs the
  app in its default language for exactly the users who needed it most.
  Mechanics: [`04`](04-launcher-ini-reference.md).
- **help.html discipline.** The template's help.html is semantic HTML
  with no CSS — it inherits the reader's fonts, sizes, and colours,
  which is the accessible default; do not add fixed colours or tiny
  fonts. Keep one `h1` then `h2`s in order; write link text that makes
  sense read aloud ("Download the manual", not "click here"); never put
  essential instructions only inside an image in `Other\Help\Images` —
  and give content images alt text. If you ship a translated help file,
  change its `lang` attribute to match.
- **Icons must survive 16×16.** The mandated icon set
  ([`01`](01-format-spec.md) §3) verifies presence, not legibility.
  Check the 16×16 rendering is recognisable, and make the 256px entry a
  real high-resolution rendering, not an upscale.
- **Choose `RunAsAdmin` values like a human will meet them.**
  `compile-force` produces a bare OS elevation prompt with no
  explanation — the worst option cognitively. Prefer `try` over `force`
  ([`12`](12-glossary-and-faq.md) FAQ), and explain in help.html why the
  app asks.
- **Beware silent aborts.** `SinglePortableAppInstance=true` aborts a
  second launch *silently* — no feedback at all, which is worst for
  screen-reader users. Only set it when the app truly cannot run twice,
  and say so in help.html.
- **Custom-code messages in plain language.** Any `MessageBox` your
  `Custom.nsh` shows is package UI. Write it so it makes sense read
  aloud, with the action it needs stated first. Whether PAL's own
  message boxes support copying their text (Ctrl+C) is **Unverified**
  in this repo — do not put information *only* in a message box; repeat
  it in help.html.
- **Do not strip the base app's accessibility features** — high-contrast
  themes, UI-automation support, language files — as "bloat" when
  trimming the package tree ([`07`](07-end-to-end-workflow.md) Phase 2).

## Accessibility checklist for packagers

- [ ] `Description` is plain language and self-contained; `Category` is
      the exact English string.
- [ ] `[Dependencies]` requirements declared honestly.
- [ ] `[Languages]`: `ENGLISH=true` present, supported languages
      enabled.
- [ ] Language chain tested: app starts in the Platform's language, and
      in the `[LanguageFile]` fallback language when launched directly.
- [ ] help.html: heading order sane, meaningful link text, no
      image-only instructions, alt text on content images, `lang`
      correct per file, `DisableSplashScreen` documented.
- [ ] Icon recognisable at 16×16; 256px entry is a genuine hi-res
      rendering.
- [ ] `RunAsAdmin` is the least surprising value that works; admin need
      explained in help.html.
- [ ] One full pass keyboard-only: install, first launch, settings
      change, exit — no mouse.
- [ ] One run under Windows high contrast: splash, help.html, and the
      app itself remain usable.

# 20 — Common Recipes

The recurring app shapes and the configuration each one needs. Every
recipe points at its full worked example or reference — this page is
the index of patterns, not a substitute for them. All keys named here
are documented in [`04-launcher-ini-reference.md`](04-launcher-ini-reference.md);
if a shape needs a behaviour no key provides, the answer is custom
code ([`05-launcher-advanced-custom-code.md`](05-launcher-advanced-custom-code.md)),
never an invented key.

## Recipe 1 — The app is already portable

**Shape:** settings in its own folder or a file beside the exe, no
registry, no `%APPDATA%`.
**Config:** a `[Launch]` section and little else. Point
`ProgramExecutable` at the exe; move the app's settings folder into
`Data\` with `[FilesMove]`/`[DirectoriesMove]` only if it writes
beside the exe (that folder is under `App\`, which upgrades replace).
**Trap:** "already portable" apps that still drop a registry key or a
`%TEMP%` file — trace before believing (docs/07).
**Full example:** [`../examples/01-natively-portable-app.md`](../examples/01-natively-portable-app.md).

## Recipe 2 — Settings in the registry

**Shape:** the app keeps settings under `HKCU\Software\Publisher\App`.
**Config:** `[Activate] Registry=true` (required), `[RegistryKeys]`
mapping a save-file name to the key, `[RegistryCleanupIfEmpty]` for
the publisher parent. PAL saves the key to `Data\settings\` while
running and backs up/restores a local copy's key automatically.
**Trap:** forgetting `[Activate]` — the registry sections are then
silently inert. Second trap: the app writes values under a *second*
key (recent-files, window state) that the trace missed.
**Full example:** [`../examples/02-registry-settings-app.md`](../examples/02-registry-settings-app.md);
the template package ([`../templates/MinimalAppPortable/`](../templates/))
is this recipe as a tree; Notepad++'s production set is in
[`../examples/real-world/notepadplusplus/`](../examples/real-world/notepadplusplus/).

## Recipe 3 — Settings in %APPDATA%

**Shape:** the app writes `%APPDATA%\Publisher\App`.
**Config:** `[DirectoriesMove]` mapping a `Data\` folder to the
`%APPDATA%` path, plus `[DirectoriesCleanupIfEmpty]` for the parent.
**Trap:** the app *also* uses `%LOCALAPPDATA%` (caches, crash dumps) —
decide per folder: move it, or leave it and accept the trace
(docs/15's user/context analysis decides which).
**Full example:** [`../examples/03-appdata-filesmove-app.md`](../examples/03-appdata-filesmove-app.md).

## Recipe 4 — Java app

**Shape:** a `.jar` or a Java-dependent exe; needs a JRE (portable
jPortable or a local install).
**Config:** `[Activate] Java=yes` — the documented values are
`yes`/`find`/`require` per docs/04 (Java discovery/requirement is an
Activate concern, not a `[Launch]` key).
**Trap:** hard-coding a Java path. Let PAL find it.
**Full example:** [`../examples/04-java-app.md`](../examples/04-java-app.md).

## Recipe 5 — Qt app

**Shape:** Qt-based; leaves Qt's own registry traces and may read
`qt.conf`.
**Config:** the app's own recipes above, **plus** `[QtKeysCleanup]`
(exact name — `[Qt]` is not a section) for Qt's registry keys.
**Trap:** shipping a `qt.conf` with absolute paths — use
`[FileWriteN]` to rewrite them per run.
**Full example:** [`../examples/05-qt-app.md`](../examples/05-qt-app.md).

## Recipe 6 — Online installer

**Shape:** the `.paf.exe` must stay small; the app downloads at
install time.
**Config:** `installer.ini` with `[DownloadFiles]`: the publisher's
canonical URL over **HTTPS**, `DownloadSHA256` set, filename/advanced
extract keys per docs/02. The launcher INI is unchanged.
**Trap:** a hash proves the payload is the file you chose, not that
it is safe — verify the publisher's file first (docs/18). Never
download over HTTP.
**Full example:** [`../examples/06-online-installer-app.md`](../examples/06-online-installer-app.md)
and [`../templates/online-installer.ini`](../templates/online-installer.ini).

## Recipe 7 — The app stores absolute paths in its config

**Shape:** the app writes `D:\path\to\file` into its own INI/XML
settings, which break when the drive letter changes.
**Config:** `[FileWrite1]`, `[FileWrite2]`, … sections rewriting the
stored paths at launch, using the `%PAL:Last*%` variables to find the
old location (reference/environment-variables.md).
**Trap:** rewriting on exit as well as entry, or a Find string that
can match user content — scope the rewrite to the exact keys the app
writes (docs/04's FileWrite semantics).

## Recipe 8 — The app needs admin (rare, justify it)

**Shape:** genuinely cannot run unelevated.
**Config:** `[Launch] RunAsAdmin=try` first; `force` only when `try`
provably fails; `compile-force` only with a written justification in
the package notes (docs/18, least elevation).
**Trap:** reaching for admin to paper over a data-redirection problem
— that problem is Recipes 2/3, not elevation.

## Recipe 9 — Single-instance app

**Shape:** the app refuses or misbehaves on a second launch, or a
second *portable* instance must not fight the first over `Data\`.
**Config:** `[Launch] SingleAppInstance` / `SinglePortableAppInstance`
per docs/04, with `WaitForOtherInstances` when cleanup must wait for
the other instance to exit.
**Trap:** enabling single-instance to hide a data-locking bug — two
instances sharing one `Data\` is the bug; the keys are the guardrail,
not the fix.

# Reference — Environment Variables

Variables the Launcher substitutes in INI values, and the standard
Windows variables packages use. Full treatment, including which are
production-verified:
[`../docs/06-environment-variables.md`](../docs/06-environment-variables.md).
**Never hard-code a drive letter or absolute path in launcher
configuration** — that is what these exist to prevent.

## %PAL:% variables (set by the Launcher)

| Variable | Expands to |
|---|---|
| `%PAL:AppDir%` | The package's `App` directory |
| `%PAL:DataDir%` | The package's `Data` directory |
| `%PAL:BinDir%` | The directory containing the launcher exe (package root) |
| `%PAL:FullAppDir%` | Full path of the app directory |
| `%PAL:PortableAppsDir%` | The PortableApps directory (the one containing the package) |
| `%PAL:PortableAppsBaseDir%` / `%PAL:PortableAppsBaseDirectory%` | The base directory above the PortableApps directory |
| `%PAL:PackagePartialDir%` | The package's path relative to the base directory |
| `%PAL:LastPackagePartialDir%` | Same, for the previous run's location (drive-change detection) |
| `%PAL:Drive%` / `%PAL:CurrentDrive%` | Current drive (with colon and backslash form per docs/06) |
| `%PAL:DriveLetter%` | Current drive letter only |
| `%PAL:DriveHex%` | Current drive in hex form |
| `%PAL:LastDrive%` / `%PAL:LastDriveLetter%` / `%PAL:LastDriveHex%` | The previous run's drive equivalents |
| `%PAL:LastPortableAppsBaseDir%` | Previous run's base directory |
| `%PAL:Bits%` | OS bitness (32/64) |
| `%PAL:LanguageCustom%` | The Platform's custom language value |

The `Last*` family is how `[FileWriteN]` sections fix paths stored by
the app when the drive letter changed between runs — see docs/04 and
docs/06 before using them.

## Standard Windows variables (as the app sees them)

`%APPDATA%`, `%LOCALAPPDATA%`, `%USERPROFILE%`, `%DOCUMENTS%`,
`%TEMP%`, `%PATH%`, `%ALLUSERSPROFILE%` — used in
`[DirectoriesMove]`/`[FilesMove]` targets and `[Environment]`
overrides. The Launcher redirects the app's view of some of these
when the corresponding sections say so; the exact semantics are in
docs/04/docs/06.

# Reference — installer.ini Quick Sections

`installer.ini` is **optional** — most packages need none. Create it
from scratch with only the sections your package needs; never copy a

# Reference — Launcher INI Quick Keys

The sections and keys reached for most often. **The full reference is
[`../docs/04-launcher-ini-reference.md`](../docs/04-launcher-ini-reference.md) —
never write a key from this quick list alone into a package without
checking its documented values there.** Unknown sections and keys
fail **silently** in PAL; [`../tools/check-package.py`](../tools/)

## Sections

| Section | Purpose |
|---|---|
| `[Launch]` | The executable and how it is launched (below) |
| `[Activate]` | Feature switches: `Registry`, `Java`, `XML`, `INI` — required companions to the sections they enable (e.g. `[RegistryKeys]` needs `Registry=true`) |
| `[RegistryKeys]` | Registry keys saved to `Data\settings\` while running, restored/removed on exit |
| `[RegistryValueWrite]` / `[RegistryValueBackupDelete]` | Individual registry values written, or backed up and deleted |
| `[RegistryCleanupIfEmpty]` / `[RegistryCleanupForce]` | Parent keys cleaned up on exit (Force deletes unconditionally — scope it narrowly, AGENTS.md) |
| `[FilesMove]` | Files (e.g. in the app's own folder or profile) redirected to `Data\` |
| `[DirectoriesMove]` | Whole directories (typically `%APPDATA%\Publisher\App`) redirected to `Data\` |
| `[DirectoriesCleanupIfEmpty]` / `[DirectoriesCleanupForce]` | Directory cleanup on exit |
| `[FileWriteN]` | Rewrites inside text config files (paths made portable) — numbered: `[FileWrite1]`, `[FileWrite2]`, … |
| `[Environment]` | Environment variables set for the app process (values use `%PAL:%` variables) |
| `[Language]` / `[LanguageFile]` / `[LanguageStrings]` | Passing the Platform language to the app |
| `[LiveMode]` | Behaviour when running from a local (non-portable) copy |
| `[QtKeysCleanup]` | Qt's registry traces (this exact name — `[Qt]` does not exist) |
| `[ServiceN]` | Services — **disabled in PAL 2.2**; do not build on it |

## [Launch] keys (the common set)

| Key | Meaning in one line |
|---|---|
| `ProgramExecutable` | Path of the real exe, relative to `App\` (backslashes) |
| `ProgramExecutableWhenParameters` | Alternate exe used when arguments are passed |
| `CommandLineArguments` / `AdditionalParameters` | Fixed arguments for the app |
| `WorkingDirectory` | Working directory for the process |
| `DirectoryMoveOK` | `yes` / `no` / `warn` — may the package folder move? Leave `warn` until move-tested |
| `SupportsUNC` | `yes` / `no` / `warn` — UNC path support; same rule |
| `SingleAppInstance` / `SinglePortableAppInstance` | Second-launch behaviour |
| `WaitForProgram` / `WaitForOtherInstances` | Launcher waits before cleanup |
| `CloseEXE` | Companion exe the launcher also waits for/closes |
| `RunAsAdmin` | `none` (default) / `try` / `force` / `compile-force` — least elevation wins (docs/18) |
| `MinOS` / `MaxOS` | Windows version window (`none`, `2000`, `XP`, `Vista`, … per docs/04) |
| `DisableSplashScreen` / `SplashTime` / `LaunchAppAfterSplash` | Splash behaviour |
| `CleanTemp` | Clean the app's `%TEMP%` traces on exit |
| `RefreshShellIcons` | Refresh shell icons after exit (file-association apps) |
| `NoSpacesInPath` | App breaks on paths containing spaces |
| `HideCommandLineWindow` | Hide the console of a command-line child |
| `RunLocally` | Live Mode: run from a local copy instead |

# Reference — Package Layout

The Format 3.9 tree at a glance. Full spec:
[`../docs/01-format-spec.md`](../docs/01-format-spec.md). Naming
rules: [`../AGENTS.md`](../AGENTS.md).

```
<AppID>/                              e.g. AppNamePortable/
  <AppID>.exe                         generated launcher (Launcher Generator)
  help.html                           package help page
  App/
    AppInfo/
      appinfo.ini                     name, AppID, versions, license, control
      appicon.ico                     icon set — exact contents in docs/01 §3
      appicon_16.png  appicon_32.png  appicon_75.png
      appicon_128.png  appicon_256.png
      installer.ini                   OPTIONAL — only the keys you need (docs/02)
      Launcher/
        <AppID>.ini                   launcher config — name matches the AppID
        Custom.nsh                    OPTIONAL launcher custom code (PAL 2.1+ home)
    <AppName>/                        the base app's binaries
    DefaultData/                      first-run defaults, copied to Data\ once
  Data/                               ALL user data and settings (runtime)
  Other/
    Help/Images/                      images referenced by help.html
    Source/
      Readme.txt                      launcher readme / licence notices
      <AppID>.ini                     example user configuration file
      PortableApps.comInstallerCustom.nsh   OPTIONAL installer custom code
```

## The rules the tree encodes

- **AppID = folder name**, and the launcher INI is named `<AppID>.ini`
  inside `App\AppInfo\Launcher\` — never a generic `launcher.ini`.
- **Binaries in `App\`, data in `Data\`, sources in `Other\Source\`.**
  Nothing user-specific is written into `App\` at runtime; no binaries
  live in `Data\`.
- `installer.ini` and `Custom.nsh` are **optional and usually absent**
  — create them only for a documented need (docs/02, docs/05).
- The generated `<AppID>.exe` is a build product of the Launcher
  Generator; `[Control] Start` in appinfo.ini names exactly it.
- Installer output: `<AppID>_<DisplayVersion>.paf.exe` (online
  installers end `_online.paf.exe`).

# Package Structure Checklist

Run against the package **source tree** before generating the launcher
and building the installer.

## Layout

- [ ] Folder is named `<AppID>` (e.g. `AppNamePortable`), no spaces.
- [ ] Package root contains only the launcher exe (once generated),
      `help.html`, and the `App` / `Data` / `Other` folders.
- [ ] Binaries are under `App\<AppName>\`; no binaries in `Data`.
- [ ] `Data` ships empty (or with only a placeholder) — no developer
      machine user data in the distributed tree.
- [ ] First-run defaults, if any, are in `App\DefaultData` mirroring the
      `Data` structure.
- [ ] Help images are in `Other\Help\Images`; sources, licenses and the
      launcher readme are in `Other\Source`.

## appinfo.ini

- [ ] `[Format] Type=PortableApps.comFormat`, `Version=3.9`.
- [ ] `AppID` equals the folder name (or correctly suffixed for
      third-party packages).
- [ ] `Category` is one of the 10 fixed values, spelled exactly.
- [ ] `Description` ≤ 512 characters; no double quotes in any field.
- [ ] `[License]` booleans are true **for this app**.
- [ ] `PackageVersion` is exactly 4 numeric parts and higher than the
      last public release.
- [ ] `DisplayVersion` matches the file name you will ship.
- [ ] `[Dependencies]` declares Java/.NET/Ghostscript/64-bit/admin
      requirements that actually apply — and none that don't.
- [ ] `[Control] Start` names the generated launcher exe exactly.
- [ ] `BaseAppID` set, or explicitly `NOT-NEEDED`.

## Icons

- [ ] `App\AppInfo\appicon.ico` contains 16/32/48 px 8-bit, 16/32/48 px
      32-bit, and 256 px PNG-compressed entries.
- [ ] `appicon_16.png`, `appicon_32.png`, `appicon_75.png`,
      `appicon_128.png`, `appicon_256.png` present, true colour + alpha.
- [ ] Multi-icon apps: `appicon1…`, `appicon2…` match `Start1`, `Start2`.
- [ ] Custom file-type icons (if `[FileTypeIcons]` uses `custom`) are in
      `App\AppInfo\FileTypeIcons` with all required sizes.

## Launcher

- [ ] Launcher INI is at `App\AppInfo\Launcher\<AppID>.ini` and its base
      name matches the launcher exe.
- [ ] Every key in the INI exists in
      `docs/04-launcher-ini-reference.md` (no invented keys).
- [ ] `[Launch] ProgramExecutable` is relative to `App\` and points at a
      file that exists in the tree.
- [ ] `[Activate] Registry=true` is present iff registry sections exist.
- [ ] `[Activate] XML=true` is present iff XML FileWrite/LanguageFile
      types are used.
- [ ] Every item in the app's trace inventory maps to a launcher
      mechanism (move, registry, FileWrite, environment, custom code).
- [ ] Numbered sections (`[FileWriteN]`, cleanup lists,
      `[RegistryValueBackupDelete]`) are consecutive starting at 1.
- [ ] No `settings` directory move (would clobber `Data\settings\*.reg`).
- [ ] Launcher has been **regenerated** after the last INI edit.
- [ ] Example user config in `Other\Source\<AppID>.ini` matches the
      keys `help.html` documents.

## installer.ini (if present)

- [ ] Contains only the features this package needs (not a copied
      full-option example).
- [ ] Online installers: `DownloadSHA256` is the real current hash of
      the publisher's file.
- [ ] `[MainDirectories] RemoveDataDirectory` is not `true`.
- [ ] Optional components actually list their directories/files.

## Security (see `docs/18-security-privacy-and-abuse.md`)

- [ ] Base app was downloaded from the publisher's canonical URL and
      verified against the publisher's signature/published hash; source
      URL and SHA-256 recorded in the project notes (bundled packages
      too, not just online installers).
- [ ] Online installers: `DownloadURL`/`DownloadKnockURL` are the
      publisher's own HTTPS addresses; `DownloadSHA256` is set.
- [ ] `RunAsAdmin` is `none`, or the value used is justified in the
      package notes and `RequiresAdmin=yes` is set in appinfo.ini.
- [ ] `[RegistryCleanupForce]` / `[DirectoriesCleanupForce]` entries are
      scoped to trees the trace inventory proved the app creates;
      `IfEmpty` variants used where they suffice.
- [ ] `[CopyLocalFiles]`, if present, copies only the documented paths,
      and help.html states what local data is imported.
- [ ] Every `.nsh` file in the tree (Custom.nsh, installer custom code,
      Debug.nsh, Legacy launchers) has been read line-by-line — none
      copied unread from AppConfigs, forums, or templates.
- [ ] No `[FilesMove]`/`[DirectoriesMove]` entry moves DLLs or scripts
      through `Data\`; `[SpecialPaths] Plugins` declared iff a real
      user-plugins folder exists.
- [ ] `DirectoryMoveOK` / `SupportsUNC` are `yes` only if the matching
      tests in `docs/08` actually passed — otherwise `warn`.

# Pre-Release Checklist

Run against the **built `.paf.exe`**, installed fresh — not against the
build tree.

## Build

- [ ] Built with the current PortableApps.com Installer (version
      recorded; not superseded by more than 30 days).
- [ ] Launcher generated with the current PortableApps.com Launcher
      from the exact INI in the package.
- [ ] Output file named `<AppID>_<DisplayVersion>.paf.exe`
      (or `..._online.paf.exe` for online installers).
- [ ] `pac_installer_log.ini` is not committed to the source repo
      (`.gitignore` covers it).

## Install + run (fresh VM or clean snapshot)

- [ ] Fresh install completes to a new `PortableApps` folder.
- [ ] App starts from the Platform menu and directly via the launcher exe.
- [ ] First run creates `Data` from `DefaultData`; defaults are sane.
- [ ] Settings persist across close/reopen.
- [ ] Package copied to a different drive letter and a path with spaces:
      works, settings and MRU intact.
- [ ] Limited (non-admin) user: works (unless admin is declared).
- [ ] Local copy coexistence: with the same app locally installed and
      configured distinctively, the portable run neither reads nor
      alters the local settings, and the local copy is unaffected after.
- [ ] Leak test: registry + filesystem snapshot compare after a full
      run-and-exit shows no leftovers outside the package folder.
- [ ] Exit paths: normal quit, and quit while a document is open, both
      clean up. Crash recovery: kill the app mid-run; next launch
      recovers without losing portable or local settings.
- [ ] File opening: double-clicking an associated file type (or Open
      With → launcher) opens the file in the app.

## Upgrade

- [ ] Previous version installed + settings created; new `.paf.exe`
      installed over it: settings preserved, binaries replaced, files
      scheduled for removal are gone, preserved directories intact.
- [ ] Installer detects the running app and offers to close it.
- [ ] Online installer only: hash verification passes with the real
      publisher file; a corrupted download fails with a clear error.

## Metadata and docs

- [ ] `PackageVersion` increased vs the last release; `DisplayVersion`
      and the file name agree.
- [ ] `help.html` renders, links work, and the user-configuration
      section matches the shipped example INI.
- [ ] `Other\Source\Readme.txt` present with the launcher GPL notice
      intact; base app license(s) included as required.
- [ ] EULA (if any) is `App\AppInfo\EULA.txt`, Unicode, and
      `EULAVersion` is correct.
- [ ] Changelog/release notes state the base app version and the
      packaging revision.

## Security pass

- [ ] Base app binaries verified against the publisher's signature or
      published hash for this exact version.
- [ ] Hostile-filename test: opening files whose names contain spaces,
      embedded quotes, and a leading dash via Open With / drag-and-drop
      opens the file and nothing else (no extra app behaviour).
- [ ] User-config test: a pre-existing `<AppID>.ini` in the package root
      with unexpected `AdditionalParameters` does not change behaviour
      beyond what help.html documents.
- [ ] `Debug.nsh` is absent from the tree and `Data\debug.log` does not
      exist in the built package.
- [ ] help.html carries the honesty statements: `Data` is plaintext
      (drive encryption recommended for sensitive apps), Live mode
      copies `Data` to the host temporarily, OS-level traces (Prefetch,
      recent-items) are outside the launcher's control, and the
      extracted folder is program files — re-install from the original
      `.paf.exe` if its provenance is in doubt.

## Accessibility pass

- [ ] Keyboard-only pass completed (install, first run, exit) and one
      run under Windows high contrast (`docs/19-accessibility.md`).
- [ ] App starts in the Platform's language; icon recognisable at
      16×16.

## Honesty check

- [ ] Anything not actually tested above is listed as **Unverified** in
      the release notes / handoff — not silently implied as tested.

# Templates

Copy-and-rename starting points. Do not write configuration files from
memory — start here or from `../examples/`.

## MinimalAppPortable/

A complete minimal package skeleton:

```
MinimalAppPortable/
  help.html
  App/
    AppInfo/
      appinfo.ini
      installer.ini            (optional-file example: preserve plugins dir)
      Launcher/
        AppNamePortable.ini    (rename to your AppID)
        Custom.nsh             (custom-code skeleton; delete if unused)
    DefaultData/
      README.txt               (explains DefaultData; replace with real defaults)
    AppName/                   (put the base app's binaries here)
  Data/                        (created on first run; do not ship user data)
  Other/
    Help/Images/               (images referenced by help.html)
    Source/
      Readme.txt               (launcher readme — keep the GPL notice text)
      AppNamePortable.ini      (example user configuration file)
```

What you must add yourself (binary files cannot be provided as text):

- `App\AppInfo\appicon.ico` and `appicon_16.png`, `appicon_32.png`,
  `appicon_75.png`, `appicon_128.png`, `appicon_256.png` — see
  `../docs/01-format-spec.md` §3 for the exact ICO contents.
- The base application's binaries in `App\AppName\`.
- The generated launcher `AppNamePortable.exe` in the package root
  (produced by the PortableApps.com Launcher Generator).

What you must rename/replace:

- Every occurrence of `AppName` / `AppNamePortable` (folder names, AppID,
  file names, `ProgramExecutable`, registry paths).
- The placeholder `appinfo.ini` metadata (Publisher, Homepage, Category,
  Description, versions, license booleans — set them to the *true* values
  for your app).
- The launcher INI's registry key and `%APPDATA%` paths — these must match
  your app's actual traces (see `../docs/07-end-to-end-workflow.md`).

## online-installer.ini

A complete `[DownloadFiles]` example for an online installer
(`..._online.paf.exe`), placed as `App\AppInfo\installer.ini`. The
SHA-256 value is a placeholder of zeros — replace it with the real hash
of the publisher's file before building.

## PortableApps.comInstallerCustom.nsh

Skeleton for installer custom code with the three supported macros
(`CustomCodePreInstall`, `CustomCodePostInstall`,
`CustomCodeOptionalCleanup`). Goes in `Other\Source\`.

## Launcher custom code (Custom.nsh)

A skeleton `Custom.nsh` is included inside the skeleton package at
`MinimalAppPortable/App/AppInfo/Launcher/Custom.nsh` — its correct home
in PAL 2.1+. Delete it if the package needs no custom code (most don't).
See `../docs/05-launcher-advanced-custom-code.md` for when custom
launcher code is appropriate.

# Tools

Standalone utilities that speed up PortableApps.com package
development. None of them need Windows or the official tools.

| Tool | What it does |
|---|---|
| [`new-package.sh`](new-package.sh) / [`new-package.ps1`](new-package.ps1) | Scaffolds a new package from [`../templates/MinimalAppPortable/`](../templates/): copies the tree, renames the folder/files to `<App>Portable`, and substitutes the app name throughout the INI files and help page. |
| [`check-package.py`](check-package.py) | Static validator for a package tree: layout, `appinfo.ini` rules (Format 3.9, 4-part PackageVersion, the 10 categories, 512-char description, no double quotes), launcher INI naming and section names (unknown sections fail **silently** in PAL — this catches them), installer.ini sections, icon/help warnings. Python 3, standard library only. |
| [`paf-data.json`](paf-data.json) | The Format data the validator uses, in machine-readable form: current tool versions, the 10 categories, launcher/installer section inventories, `[Launch]`/`[Activate]` keys, and the `%PAL:%` environment variables. |
| [`package.gitignore`](package.gitignore) | `.gitignore` for a package source repo — keeps the generated `pac_installer_log.ini` and build outputs out (AGENTS.md rule). |
| [`build-ai-bundle.py`](build-ai-bundle.py) | Regenerates the repo-root `manifest.json` (machine-readable file map + reading order) and `ai-bundle.md` (the whole knowledge base as one file) so AI tools that download the repo — ChatGPT included — can ingest it locally. Run after any content change. |

Usage examples are in each file's header. The validator's inventories
come from `docs/01`, `docs/02`, `docs/04`, and `AGENTS.md` of this
repo; when the Format's documentation changes, update
`paf-data.json` and `check-package.py` together.
